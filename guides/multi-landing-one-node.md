# 同一节点挂多台落地：面板配置思路

刚起步时，很多人只有一台落地机，面板里一个节点就能跑。等用户多起来、想多铺几个地区，或者想把日本、美国、香港的出口分开，就会遇到一个问题：面板里的「节点」到底对应什么？是一台物理机，还是一个出口，还是一条线路？这篇先把这个概念掰开，再给出三种常见的「同一节点挂多台落地」配置思路，重点讲最稳的那一种怎么做，顺带说清另外两种适合什么场景、容易踩什么坑。

先说结论：**面板里的一个节点，最好只对应一台落地机上的一个 V2bX 实例**。一台物理机可以跑多个节点，但一个面板节点不要同时挂多台落地机——流量统计、在线状态、故障定位都会乱。所谓「同一节点挂多台落地」，实际操作时往往是反过来的：用一台入口机、一个面板分组，把多台落地机组织成一套对外可用的节点体系。

## 先理清三个概念

- **面板节点**：Xboard 后台里的一条节点记录，有独立的 NodeID、名称、地址、端口和测速信息。用户订阅里看到的每一条，基本都对应一个面板节点。
- **节点端（V2bX）**：跑在落地机上的程序，定时向面板拉取自己那个 NodeID 的配置，并把流量上报回面板。一个 V2bX 进程可以拉多个 NodeID，但每个 NodeID 仍然只对应一组协议配置。
- **落地机**：真正出网的服务器。用户流量最终从哪台机器的 IP 出去，落地就是哪台。同一台落地机可以同时是多条线路的出口，但一台落地机出问题时，挂在它上面的节点会一起受影响。

把这三层分开，后面的配置就不会乱：一对一最清晰，一对多只在有明确理由时才用。

## 方案一（推荐）：一落地一节点，各自独立

这是最不容易出错的做法：有几台落地机，面板里就建几个节点，每台落地机单独装 V2bX，各自只拉自己的 NodeID。

### 第 1 步：面板里建节点

在 Xboard 后台进入节点管理，按落地机逐个添加，关键字段按下面这样填：

- 名称：用「地区-线路-序号」的固定格式，例如 `日本-家宽-01`、`美国-普通-01`，不要只写 `节点1`、`节点2`，以后排查时分不清。
- 地址：填这台落地机给用户连接的域名或 IP，例如 `jp01.example.com`，不要填面板机地址。
- 端口：每台落地机独立分配，避免和面板、其他服务撞端口。
- 分组：把同一批节点放进同一个用户组，套餐可见性由分组控制，而不是靠改名字来区分。

建完后记下每个节点对应的 NodeID，例如日本落地是 `101`、美国落地是 `102`。NodeID 是面板和 V2bX 对接的唯一钥匙，抄错一位就会出现节点离线或配置串位。

### 第 2 步：每台落地机装 V2bX，只拉自己的 NodeID

登录每台落地机，安装并配置 V2bX，核心是让它只认自己那个 NodeID：

```json
{
  "Log": {
    "Level": "warning"
  },
  "Nodes": [
    {
      "PanelType": "V2board",
      "ApiConfig": {
        "ApiHost": "https://panel.example.com",
        "ApiKey": "面板后台生成的通讯密钥",
        "NodeID": 101,
        "NodeType": "VLESS",
        "Timeout": 30,
        "EnableVless": true
      },
      "ControllerConfig": {
        "ListenIP": "0.0.0.0",
        "UpdatePeriodic": 60
      }
    }
  ]
}
```

> 为什么只写一个 NodeID？一个 V2bX 实例只拉一个节点时，日志里报错直接对应这台落地机，流量上报也不会和其他节点混在一起。等这套跑稳了，再考虑一台机器跑多个 NodeID 也不迟。

每台落地机改完配置后重启 V2bX，回到面板看节点状态：状态变成在线、且有流量上报，说明这一路通了。有一台不通就只查这一台，不要把所有落地机一起重装。

### 第 3 步：用分组控制用户能看到哪些落地

节点建得多，用户订阅里会一下子冒出十几条，反而不知道选哪个。正确做法不是少建节点，而是用分组收敛：

- 按套餐分组：基础套餐只看到普通线路组，家宽套餐再看到家宽组。
- 按地区分组：把日本、美国、香港的节点分别放进对应的组，套餐绑定组即可。
- 命名保持一致：同一组里的节点名称前缀相同，用户一眼能看出这是同一批出口。

这样「多台落地」对用户来说是「多个可选节点」，对你来说是「多个独立统计单元」，两边都不乱。

## 方案二：一台入口机 + 多台落地机

有些场景确实需要「一个入口、多个出口」：比如入口 IP 比较干净、适合做连接点，但出口想分散到不同地区；或者想先让用户连到一台中转机，再由中转机把流量送到不同的落地机。

这种结构里，面板节点仍然按落地机分开建，入口机本身不跑协议服务端，只做转发。转发层可以用 realm 这类轻量工具，把入口端口转发到对应落地机的端口：

```bash
# 入口机上的 realm 配置示例（示例域名/IP，按实际填写）
# 监听 10001 转发到日本落地，监听 10002 转发到美国落地
# realm.toml
[[endpoints]]
listen = "0.0.0.0:10001"
remote = "jp01.example.com:443"

[[endpoints]]
listen = "0.0.0.0:10002"
remote = "us01.example.com:443"
```

这套结构要特别注意两点：一是入口机和落地机之间的链路本身也会消耗带宽和增加延迟，晚高峰先卡的往往是入口机；二是如果入口机和落地机都向面板上报流量，同一份流量可能被算两次，计费口径要提前定好——一般只以落地机的上报为准，入口机只做转发、不计入面板统计。关于入口机和落地机怎么分工，可以对照[面板机与落地机分离部署](panel-node-separation.md)里的思路一起看。

## 方案三：一台机器跑多个 NodeID

V2bX 支持一个进程拉多个 NodeID，配置里 `Nodes` 数组写多个节点即可。这适合「一台物理机、多个端口、多种协议」的场景，例如同一台落地机上同时提供 VLESS 和 Hysteria2 两个节点。

```json
{
  "Nodes": [
    {
      "PanelType": "V2board",
      "ApiConfig": {
        "ApiHost": "https://panel.example.com",
        "ApiKey": "面板后台生成的通讯密钥",
        "NodeID": 101,
        "NodeType": "VLESS"
      }
    },
    {
      "PanelType": "V2board",
      "ApiConfig": {
        "ApiHost": "https://panel.example.com",
        "ApiKey": "面板后台生成的通讯密钥",
        "NodeID": 102,
        "NodeType": "Hysteria2"
      }
    }
  ]
}
```

这个方案省机器，但风险也集中：这台机器一挂，上面挂的所有节点同时离线；某一个 NodeID 的配置写错，日志里要先分清是哪个节点的问题再动手。所以它适合「同一台落地机、多个协议」，不适合「多台落地机共用一个 NodeID」——后者一旦出问题，你连先查哪台机器都说不清。

## 验证：按这个顺序查一遍

新节点上线后，不要只看面板显示在线就收工，按下面顺序验证：

1. **面板状态**：每个 NodeID 都在线，且在线状态和对应的落地机一一对应，没有两个节点共用一个 NodeID。
2. **端口监听**：在每台落地机上跑 `ss -tlnp | grep 端口号`，确认 V2bX 确实在监听面板里填的那个端口，而不是只在面板里「看起来在线」。
3. **出口 IP**：在每台落地机上跑 `curl ip.sb`（或你常用的 IP 查询地址），确认出网 IP 和你预期的地区一致——日本落地不要从美国 IP 出去。
4. **流量上报**：面板里每个节点的流量在变化，且变化量和实际使用量级对得上。如果某节点长期在线但流量永远是 0，先查它的 NodeID 和 ApiKey 有没有抄错。
5. **订阅内容**：用一个测试账号拉一次订阅，确认订阅里的节点数量、名称、分组和面板后台一致，没有重复节点，也没有不该出现的节点。

## 常见坑

- **NodeID 重复**：两台落地机填了同一个 NodeID，面板上一个在线、一个离线来回跳，或者流量全算到其中一个头上。发现这种现象先对 NodeID，不要先重启。
- **地址填成面板机**：节点地址填了面板域名，用户连过去的是面板机，自然连不上协议端口。节点地址永远填落地机的域名或 IP。
- **端口冲突**：落地机上 V2bX 的端口和已有的 Web 服务、其他协议撞了，V2bX 起不来或起来后立刻退出。先 `ss -tlnp` 看占用，再改端口。
- **ApiKey 泄露**：通讯密钥不要贴到公开文档、截图或群聊里。换过密钥后，所有用这个密钥的 V2bX 都要同步改，否则会批量离线。
- **节点名起得太随意**：`节点1`、`新节点`、`test` 这类名字，三个月后你自己都不知道它对应哪台机器。建节点时就按「地区-线路-序号」命名，后续交接和排查都省时间。
- **中转和落地重复计费**：用了方案二的入口转发，又让入口机和落地机同时上报流量，用户的剩余流量会掉得比实际快。计费口径定一个唯一来源，并写进自己的运维笔记。

## 小结

同一节点挂多台落地的正确姿势，不是把多台机器塞进一个 NodeID，而是把每一台落地机拆成独立的面板节点，再用分组把它们组织起来。需要统一入口时加一台转发机，需要多协议时一台机器跑多个 NodeID，但「一个 NodeID 只对应一台落地机」这条底线不要破。按这个结构扩容时，加一台落地机就是「面板建一个节点、机器上装一个 V2bX、验证一遍流量」三步，不用动已有的节点，扩容和排障都不会互相干扰。

# VPS 安全基线：改 SSH 端口、密钥登录、关密码

刚买到一台 VPS、装好面板和节点端，很多人第一件事是急着把服务跑起来，SSH 安全却一直用着默认配置：22 端口、root 密码登录、密码还是建机时随手设的那一个。这样的机器上线没几天，登录日志里就会出现成串的爆破尝试——虽然不一定能爆破成功，但一旦密码强度不够、或者哪天某个服务泄露了口令，整台面板机、连同上面所有节点配置都会一起丢。下面这套基线不改任何业务配置，只动 SSH 本身，按顺序做完，一台 VPS 的登录面就能收得很干净。

## 动手前先说清楚：顺序错了会把自己锁在门外

这篇教程里最重要的一条不是某个参数，而是操作顺序：先把密钥登录配通并验证能用新方式登录成功，再去改端口、关密码。顺序反过来——比如先关了密码登录、密钥却没配好——结果就是连自己都登不进去，只能走云厂商的控制台救援，既费时间又容易在慌乱中改错更多配置。

所以整篇按下面这个顺序来，每一步做完都验证通过再往下一步走：

1. 本地生成密钥对，把公钥传到服务器。
2. 改 SSH 端口，重启服务，用新端口验证登录。
3. 确认密钥登录没问题后，关闭密码登录。
4. 检查防火墙和云厂商安全组，确保新端口是放行的。

开始之前，先确认你手头有一台能正常 SSH 登录的机器，以及本地电脑上的终端。下面的命令以 Debian / Ubuntu 为例，其他发行版的配置文件路径基本一致，只有服务重启命令可能略有不同。

## 第一步：本地生成密钥对，公钥传上服务器

密钥登录的原理很简单：私钥留在你自己的电脑上，公钥放在服务器上，登录时服务器用公钥验证你手里的私钥，配对成功才放行。密码再也不用在网络上传输，爆破也就无从下手。

```bash
# 在本地电脑上生成密钥对（不要在服务器上生成再下载私钥）
# -t ed25519 是目前推荐的算法，又短又安全；老系统不支持时再改用 rsa
ssh-keygen -t ed25519 -C "你的标识，例如 admin@example.com"

# 生成时会问保存位置，直接回车用默认路径即可
# 接着会问是否给私钥设一个口令（passphrase）：建议设一个
# 私钥口令是第二道锁，即使私钥文件泄露，没有口令也用不了
# 生成后会得到两个文件：
#   ~/.ssh/id_ed25519      私钥，绝不要发给任何人、不要贴到工单或群里
#   ~/.ssh/id_ed25519.pub  公钥，可以公开，传到服务器的就是它
```

> 为什么私钥要在本地生成、而不是在服务器上生成再下载？私钥一旦在服务器上生成，传输回本地的过程中就多了一次暴露机会；本地生成则私钥从不出本机，从源头上少了一个泄露环节。

把公钥传到服务器，最省事的办法是用 `ssh-copy-id`：

```bash
# 把本地公钥追加到服务器对应用户的 authorized_keys
# 第一次执行时还是用密码登录，传完之后就可以用密钥登录了
ssh-copy-id -i ~/.ssh/id_ed25519.pub root@你的服务器IP

# 如果你要登录的不是 root，而是普通用户，把 root 换成那个用户名
# ssh-copy-id -i ~/.ssh/id_ed25519.pub deploy@你的服务器IP
```

传完后立刻验证密钥登录是否生效，先不要动任何配置：

```bash
# 这次登录应该不再问密码，而是直接进系统
# 如果设了私钥口令，会问一次私钥口令，这是正常的
ssh -i ~/.ssh/id_ed25519 root@你的服务器IP

# 进系统后确认公钥确实在 authorized_keys 里
cat ~/.ssh/authorized_keys
```

> 为什么要先验证、再改配置？因为这一步是后面所有操作的安全网。密钥登录验证通过，意味着即使后面关掉密码登录，你也还有一条能进门的路；验证没通过就继续往下改，等于先把后路断了。

如果你有多台电脑都要管理这台服务器，给每台电脑单独生成一对密钥、分别把公钥传上去，不要把同一个私钥文件拷来拷去。一台电脑丢了，只删它对应的公钥就行，其他电脑不受影响。

## 第二步：改 SSH 端口，避开默认 22 端口的扫描

改端口防不住定向攻击，但能挡掉绝大多数针对 22 端口的自动化扫描和爆破，登录日志立刻会清净很多。这一步的成本很低：改一个数字、重启一次服务、以后登录时多加一个 `-p` 参数。

```bash
# 先登录服务器，编辑 SSH 服务端配置
sudo vim /etc/ssh/sshd_config

# 找到下面这几行，按说明修改（去掉行首的 # 号，改成你要的值）
# Port：改成一个 1024 以上、不与面板、节点端、数据库等服务冲突的端口
# 例如 22222，具体数字自定，记住它
Port 22222

# PermitRootLogin：如果你平时用普通用户 + sudo 管理，顺手改成 no
# 如果你确实需要 root 直接登录，先保持 yes，等密钥登录稳定后再决定
# PermitRootLogin prohibit-password
# 这一行的意思是：root 可以登录，但只允许密钥登录、不允许密码登录
# 是比直接禁 root 更稳妥的过渡选项
```

改完保存，重启 SSH 服务并确认新端口在监听：

```bash
# Debian / Ubuntu 重启 SSH 服务
sudo systemctl restart ssh
# 有些系统服务名是 sshd，上面那条报错时改用下面这条
# sudo systemctl restart sshd

# 确认新端口在监听、旧端口不再监听
sudo ss -tlnp | grep 22222

# 不要关掉当前这个 SSH 会话！新开一个终端窗口，用新端口登录验证
# ssh -p 22222 root@你的服务器IP
```

> 为什么一定要保留当前会话、新开窗口验证？如果新端口被防火墙挡住、或者配置文件写错导致服务没起来，当前这个旧会话是你最后的修复通道。先验证新端口能进，再关旧窗口；新端口验证失败时，旧会话还在，改回来只要一分钟。

新端口验证通过后，顺手更新你本地的 SSH 配置，以后登录就不用每次都敲 `-p`：

```bash
# 本地 ~/.ssh/config 里加一段（域名与 IP 均为占位符）
Host 我的面板机
    HostName 203.0.113.10
    Port 22222
    User root
    IdentityFile ~/.ssh/id_ed25519

# 之后直接用别名登录即可
# ssh 我的面板机
```

## 第三步：确认无误后，关闭密码登录

这是整套基线里最关键的一步，也是最容易把自己锁死的一步，所以必须满足两个前提再动手：第一，密钥登录已经验证通过；第二，新端口登录也已经验证通过。两个前提都满足，再改下面这几项：

```bash
# 编辑 /etc/ssh/sshd_config，找到并改成下面这样
# PasswordAuthentication：彻底关闭密码登录，只认密钥
PasswordAuthentication no

# ChallengeResponseAuthentication：老系统的质询式登录，一并关掉
ChallengeResponseAuthentication no

# PubkeyAuthentication：确保密钥登录是开启的
PubkeyAuthentication yes

# 如果之前 PermitRootLogin 还保持 yes，现在可以按需收紧
# 只用普通用户管理的机器，改成下面这样更干净
# PermitRootLogin no
```

改完重启服务，然后做一次决定性的验证：新开终端，用密钥登录应该成功；故意用密码登录应该被拒绝。

```bash
# 重启服务
sudo systemctl restart ssh

# 新开终端验证：密钥登录应该直接成功
ssh -p 22222 root@你的服务器IP

# 再验证密码登录确实被拒绝了（会直接提示 Permission denied，不再问密码）
# ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no -p 22222 root@你的服务器IP
```

> 为什么关密码登录比“设一个很强的密码”更彻底？强密码只能提高爆破成本，攻击者可以无限次尝试；关掉密码登录后，密码认证这个入口本身就不存在了，爆破脚本连尝试的机会都没有。密钥的强度也不依赖人的记忆力，ed25519 密钥的破解难度远高于任何能记住的密码。

## 第四步：防火墙和云厂商安全组，别让新端口死在门外

很多人在这一步栽跟头：sshd_config 改对了、服务也起来了，登录却超时。原因往往不在 SSH 本身，而在防火墙——机内防火墙放行了 22，却没放行新端口；或者云厂商安全组只放行了 22，新端口在云平台那一层就被拦住了。两边都要检查：

```bash
# 以 ufw 为例：放行新端口，同时确认旧端口规则的处理
sudo ufw allow 22222/tcp
sudo ufw status numbered

# 确认新端口登录没问题后，再删掉 22 端口的放行规则
# sudo ufw delete allow 22/tcp
# 注意：删 22 之前务必确认新端口已经能登录，否则先留着 22 应急

# 以 firewalld 为例
# sudo firewall-cmd --permanent --add-port=22222/tcp
# sudo firewall-cmd --reload
# sudo firewall-cmd --list-ports
```

云厂商安全组（阿里云、腾讯云、AWS 等控制台里的安全组 / 防火墙规则）也要同步改：入方向放行新端口的 TCP，确认无误后再移除 22 的规则。机内防火墙和云厂商安全组是两道门，只开一道等于没开，排查超时问题时先查这两道门，再怀疑 SSH 配置。

> 为什么排查登录超时要先查防火墙、而不是先改 SSH 配置？超时（connection timed out）和拒绝（Permission denied）是两种完全不同的症状：超时说明包根本没到 SSH 服务，大概率是防火墙或安全组拦了；拒绝说明包到了、认证没过，才是配置或密钥的问题。先分清症状，能省掉大量无用排查。

## 面板机和节点端，基线做法有什么不同

上面这套流程对面板机和落地机都适用，但侧重点略有不同：

- **面板机**：面板后台本身就是敏感入口，SSH 基线之外，还要把面板后台的访问也收紧。面板机到节点端的 API 回连端口只允许面板 IP 访问，具体做法可以对照本仓库的 [节点端 API 防护：只允许面板 IP 访问](node-api-firewall.md)，SSH 基线和 API 防护两层加起来，面板机的入口才算真正收干净。
- **落地机**：落地机上跑的是协议服务端，SSH 端口改掉后，协议端口（例如 443、8443）不受影响，不用跟着改。落地机往往有多台，建议每台用不同的 SSH 端口、不同的密钥对，一台出问题不牵连其他机器。
- **普通用户还是 root**：条件允许的话，给日常管理建一个普通用户、加入 sudo 组，SSH 只允许这个用户登录，root 直接禁掉。面板安装脚本有些要求 root 执行，执行时用 `sudo` 提权即可，日常登录没必要一直拿着 root。

## 验证清单：做完这四步，对照打一遍勾

```bash
# 1. 密钥登录成功（不输服务器密码，只输私钥口令或直接进系统）
ssh -p 22222 root@你的服务器IP

# 2. 密码登录被拒绝（不再问密码，直接 Permission denied）
# ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no -p 22222 root@你的服务器IP

# 3. 新端口在监听，旧端口 22 不再监听
sudo ss -tlnp | grep -E '22222|22'

# 4. 防火墙和云厂商安全组都放行了新端口
sudo ufw status numbered

# 5. 登录日志里看不到成串的爆破记录了（过一两天再看更明显）
sudo grep "Failed password" /var/log/auth.log | tail -20
```

五项都通过，这台 VPS 的 SSH 基线就算立住了。之后新增机器时，把这套流程当成装机清单的第一项：密钥先行、端口改掉、密码关掉、防火墙对齐——四步走完再装面板、再接节点，顺序对了，后面基本不用再为登录安全返工。

## 常见坑汇总

- **先关密码、后配密钥**：顺序反了等于自锁，只能走云厂商控制台救援，改配置前先确认密钥登录已通。
- **改完端口就关掉当前会话**：新端口万一被防火墙挡住，旧会话是你唯一的修复通道，验证通过再关。
- **只改机内防火墙、不改云厂商安全组**：两道门都要放行新端口，只开一道照样超时。
- **私钥发到群里、贴到工单或拷给多人共用**：私钥泄露等于门钥匙泄露，一人一对密钥，丢了只删对应公钥。
- **私钥不设口令**：电脑丢了等于服务器也丢了，生成密钥时设一个私钥口令，多一道保险。
- **改端口后面板脚本还用默认 22 连接**：有些一键脚本或面板的节点添加流程默认走 22，改端口后要同步更新脚本里的端口参数，否则节点添加会失败。
- **PermitRootLogin 直接改成 no、却没有普通用户**：禁 root 之前先建好普通用户并确认能 sudo，否则连提权入口都没了。
- **配置文件改错一个字符导致服务起不来**：重启前先用 `sshd -t` 检查配置语法，报错先修再重启。
- **只在一台机器上做基线**：面板机、落地机每台都要单独做，一台没做就是整个架构的短板。
- **做完基线就不管了**：定期看一眼登录日志和 authorized_keys，多余的旧公钥及时清理，离职或换电脑时第一时间删对应密钥。

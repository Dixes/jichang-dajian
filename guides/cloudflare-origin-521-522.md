# Cloudflare 回源 521/522 导致面板订阅拉取失败：源站端口与防火墙排查

面板域名套了 Cloudflare 之后，浏览器打开面板却报 521 Web Server Is Down，或者订阅链接拉取时报 522 Connection Timed Out，这两个报错都指向同一个方向：Cloudflare 的边缘节点联系不上你的源站。问题不一定在面板本身，很可能出在源站端口、防火墙或者 Cloudflare 回源模式这一段。下面按先定位、再分段排查的顺序来，多数情况不用重装面板就能恢复。

## 先分清：521 和 522 不是同一个问题

同样是打不开面板，521 和 522 的排查起点完全不同，先看报错代码再动手：

- **521 Web Server Is Down**：Cloudflare 去连源站时直接被拒绝了。源站服务没起来、端口没监听，或者防火墙把 Cloudflare 的回源 IP 挡在外面，都会报 521。
- **522 Connection Timed Out**：Cloudflare 连上了源站方向，但等不到响应就超时了。源站负载过高、反代上游响应太慢、或者 TCP 连接被中间设备静默丢弃，常见表现为 522。

分清代码之后，521 先查「能不能连上」，522 先查「连上之后为什么没响应」，不要两条线混着查。

## 第一步：绕过 Cloudflare，确认源站本身活着

排障的第一原则是缩小范围。先绕过 Cloudflare，直接访问源站，看面板本身有没有问题：

```bash
# 1. 确认面板服务在跑，服务名以你部署时的实际名称为准
systemctl status xboard

# 2. 确认面板监听端口在列，端口换成你自己的实际端口
ss -tlnp | grep -E '8080|8000|9000'

# 3. 在源站本机直接访问面板，绕过反代和 Cloudflare
curl -I http://127.0.0.1:8080
```

如果本机直连就失败，先按面板服务、数据库、端口占用这个顺序修，这是源站自己的问题，跟 Cloudflare 无关。如果本机直连正常，再用源站 IP 直接访问一次（先临时确认防火墙允许你自己的测试 IP）：

```bash
# 用源站 IP 直接访问，确认反代层也能响应
curl -I http://203.0.113.10:8080
```

这里的 IP 和端口都是占位符，换成你自己的源站 IP 和面板端口。源站 IP 直连也正常，说明问题确实出在 Cloudflare 到源站这一段，再往下走。

## 第二步：521 重点查防火墙与源站端口

521 最常见的根因，是源站防火墙只放行了 80/443，却没放行 Cloudflare 的回源 IP 段，或者面板端口根本没有对外监听。按下面顺序核对：

```bash
# 查看当前防火墙规则，确认 80 和 443 是否放行
iptables -L -n | grep -E '80|443'
# 如果用的是 ufw，规则长这样
ufw status numbered
```

如果你在源站上做了「只允许 Cloudflare 回源 IP 访问 80/443」的白名单，这是正确做法，但白名单要定期跟 Cloudflare 官方公布的 IP 段对齐——Cloudflare 回源 IP 段会更新，旧的白名单一旦过期，新的边缘节点连进来就会被挡，表现就是间歇性 521，今天能打开、明天打不开。核对时注意两点：

- 白名单里是 Cloudflare 的回源 IP 段，不是你自己的办公 IP，也不是面板机的内网 IP。
- 如果你同时开了云厂商的安全组，安全组和服务器本机防火墙要同时放行，只放一层还是会被挡。

还有一种容易忽略的情况：面板只监听了 127.0.0.1，反代却配置在另一台机器，或者 Cloudflare 回源走的是源站公网 IP。反代在本机时用 127.0.0.1 没问题，但如果回源流量要先经过本机防火墙再进反代，监听地址和反代配置必须对应起来。核对反代配置里的上游指向：

```nginx
server {
    listen 80;
    server_name panel.example.com;

    location / {
        # 必须指向面板实际监听的地址和端口
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

如果你之前用的是橙云和灰云两种模式混搭，域名解析方式不同也会影响回源路径，可以先对照本仓库的另一篇教程理清两种模式的区别：[Cloudflare 橙云和灰云对节点有什么影响](guides/cloudflare-orange-vs-grey.md)。

## 第三步：522 重点查 SSL 模式与超时

源站能连上但 522，接下来查两个最常见的点：Cloudflare 的 SSL 模式和源站响应超时。

Cloudflare 的 SSL 模式要和源站的证书配置匹配，错配时握手会在边缘节点和源站之间卡住，最终超时成 522：

- **灵活模式（Flexible）**：Cloudflare 到源站走 HTTP，不要求源站有证书。如果源站强制跳转 HTTPS，或者反代配置了 HSTS，灵活模式下容易出现重定向循环和超时。
- **完全模式（Full）**：Cloudflare 到源站走 HTTPS，但不校验源站证书是否受信任。源站需要有证书，哪怕是自签证书也可以。
- **完全严格模式（Full Strict）**：Cloudflare 到源站走 HTTPS，且要求源站证书受信任。源站证书过期、自签、或者域名对不上，都会导致回源失败。

选择原则很简单：源站有受信任证书就用完全严格模式，源站只有自签证书就用完全模式，不要用灵活模式去套一个强制 HTTPS 的源站。改完 SSL 模式后，到 Cloudflare 控制台清一次缓存，再重新访问，避免旧的边缘缓存干扰判断。

如果 SSL 模式没问题，再看超时。订阅生成、节点统计这类接口响应比较慢，源站处理时间一长，Cloudflare 等不到响应就断开，表现就是订阅页面 522、首页却正常。先看反代的超时参数，再看源站负载：

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_connect_timeout 10s;
    proxy_send_timeout 60s;
    proxy_read_timeout 120s;
}
```

`proxy_read_timeout` 是等上游回响应的时间，订阅生成这类慢接口主要靠它兜底。调大之后如果 522 消失，说明就是慢响应问题；如果还是频繁出现，就要看源站是不是 CPU 或内存长期吃满，那是资源问题，不是光调超时能解决的。

## 验证：确认回源真的通了

不要只刷一次浏览器就宣布修好，按下面三步验证：

```bash
# 1. 源站本机直连面板，应当返回 200 或 302
curl -I http://127.0.0.1:8080

# 2. 用灰云方式（直接解析到源站 IP 的测试域名）访问一次，确认源站对外可达
curl -I https://test-panel.example.com

# 3. 切回橙云，再访问一次正式域名，确认不再出现 521 或 522
curl -I https://panel.example.com
```

三步都通过后，再用浏览器无痕模式打开面板，登录一次、拉取一次订阅链接、打开一次节点列表——这几个动作都正常，才算真正通过。只验证首页是不够的，慢接口的问题往往藏在订阅生成页。

## 常见坑

- **只放行了 80，没放行 443**：Cloudflare 回源走 HTTPS 时需要 443，只放 80 会导致 HTTPS 回源直接被挡，报 521。
- **白名单用了过期的 Cloudflare IP 段**：回源 IP 段会更新，白名单要定期对齐官方最新列表，否则会出现间歇性 521。
- **SSL 模式和源站证书不匹配**：灵活模式套强制 HTTPS 的源站、完全严格模式套自签证书，都是典型的 522 来源，改模式之前先确认源站证书状态。
- **把 521/522 和 502 混为一谈**：502 是反代没拿到上游有效响应，521/522 是 Cloudflare 没拿到源站响应。先看浏览器报错代码再动手，方向错了会越修越乱。
- **改完配置忘了清缓存**：Cloudflare 边缘缓存可能还留着旧的错误页，改完源站和 SSL 模式后要清一次缓存再验证，否则会误判为没修好。

# Hysteria2 和 VLESS Reality 到底选哪个

刚把面板和节点端搭起来，接下来最纠结的一步往往是：节点到底上 Hysteria2，还是 VLESS + Reality？两个协议都能跑、都能出订阅，网上又各有一堆“吊打对方”的说法，结果越看越拿不定主意。其实这两个协议解决的问题并不完全一样：Hysteria2 擅长在弱网和晚高峰下把速度拉起来，VLESS Reality 擅长把流量伪装得像正常网站访问、降低被识别的概率。选错不是不能用，而是会在你最在意的那个场景上吃亏。下面按服务端搭建的视角，把两者的差别、配置和取舍讲清楚，帮你一次定下来。

## 先说结论：按你的用户和线路选，不按热度选

如果你要先定一个默认答案，可以按下面这条规则来：

- 用户主要在晚高峰、移动网络、跨国线路不稳定的环境下用，对速度和延迟敏感，优先选 **Hysteria2**。
- 用户分布在审查较严的地区，或者你希望节点流量在常规检测下更像正常 HTTPS 访问，优先选 **VLESS + Reality**。
- 不确定、两种用户都有，最稳妥的做法是 **两个都上**：同一台落地机同时跑 Hysteria2 和 VLESS Reality 两个入站，面板里做成两个节点或一个节点的两个协议入口，让订阅端按需选择。服务端多花十几分钟配置，换来的是不用事后返工。

为什么不建议只看“哪个更快”就拍板？因为速度测试结果高度依赖测试时间、测试线路和对端网络环境，晚高峰测出来 Hysteria2 快，不代表白天、不好网络下结论不变；反过来，Reality 在某些线路上延迟更低，也不代表它在丢包严重的网络下同样稳。协议选型首先是场景选型，其次才是性能对比。

## 两者到底有什么不同

从服务端实现的角度看，两者的核心差别在传输层和伪装方式上：

| 维度 | Hysteria2 | VLESS + Reality |
| --- | --- | --- |
| 传输协议 | 基于 QUIC（UDP） | 基于 TCP + TLS |
| 弱网表现 | 丢包、抖动下恢复较快，晚高峰优势明显 | 依赖 TCP，丢包严重时延迟上升较快 |
| 伪装方式 | 自带 TLS 加密，流量特征相对明显 | Reality 借用真实网站的 TLS 指纹，握手看起来像访问目标站 |
| 端口与证书 | 不依赖域名证书，UDP 端口即可工作 | 不需要自己申请证书，但需要一个可借用的目标域名（dest） |
| 防火墙友好度 | 有些网络会限速或拦截 UDP，需要实测 | TCP 443 走得通的地方一般都能通 |
| 服务端组件 | Hysteria2 独立服务端 | 常用 Xray 或 sing-box 做服务端 |
| 运维复杂度 | 配置简单，调优项集中在拥塞控制和端口上 | 配置项多，密钥、指纹、dest 三处错一处就连不上 |

一句话总结：Hysteria2 是“跑得快”的路线，VLESS Reality 是“藏得像”的路线。你的落地机线路质量、用户所在地区的网络环境，决定了哪条路线更值得优先。

## Hysteria2 服务端：最小可用配置

Hysteria2 的服务端配置相对简单，核心就三样：监听端口、密码、证书。证书可以用自签，服务端自己生成即可，不需要去申请域名证书，这也是它部署快的原因之一。

```yaml
# /etc/hysteria/config.yaml（示例，域名与 IP 均为占位符）
listen: :443

tls:
  type: acme
  acme:
    domains:
      - node.example.com
    email: admin@example.com
  # 没有域名时也可以用自签证书：
  # type: self-signed

auth:
  type: password
  password: 请换成你自己的强密码

masquerade:
  type: proxy
  proxy:
    url: https://example.com
    rewriteHost: true

# 带宽与拥塞控制：先按默认值跑，实测有瓶颈再调
# 下面两个值是服务端向客户端宣告的上下行带宽，不是硬限速
# 填得过高会导致拥塞控制误判，填得过低则跑不满带宽
```

> 为什么 masquerade 值得配一下？Hysteria2 的端口被直接探测时，如果没有任何伪装内容，空响应本身就是一种特征。配一个反代伪装后，探测者打开看到的是一个正常网站，至少不会一眼看出这是一个协议入口。

启动并检查端口是否在监听：

```bash
# 启动 Hysteria2 服务端（以 systemd 为例，具体服务名以你安装的方式为准）
systemctl enable --now hysteria-server

# 确认 UDP 端口在监听：Hysteria2 走 UDP，TCP 的端口检查工具看不到它
ss -ulnp | grep 443

# 查看启动日志，确认没有证书或端口占用报错
journalctl -u hysteria-server -n 50 --no-pager
```

> 为什么要用 `ss -ulnp` 而不是只看 TCP？Hysteria2 基于 QUIC，走的是 UDP，只查 TCP 监听会误以为服务没起来，白白去排查配置问题。

## VLESS + Reality 服务端：最小可用配置

VLESS Reality 的服务端通常用 Xray 或 sing-box，下面以 Xray 的入站配置为例。关键参数有三个：UUID、Reality 私钥和公钥、借用目标站（dest）。dest 的选择有讲究：要选一个真实存在、支持 TLS 1.3、且与你服务器地区和网络环境匹配的大站，具体挑选方法可以对照本仓库的 [Reality 的 dest 怎么选：借用站点与密钥生成](reality-dest-guide.md) 一步步来。

```json
{
  "inbounds": [
    {
      "port": 443,
      "protocol": "vless",
      "settings": {
        "clients": [
          {
            "id": "请换成你自己生成的 UUID",
            "flow": "xtls-rprx-vision"
          }
        ],
        "decryption": "none"
      },
      "streamSettings": {
        "network": "tcp",
        "security": "reality",
        "realitySettings": {
          "show": false,
          "dest": "www.example.com:443",
          "xver": 0,
          "serverNames": ["www.example.com"],
          "privateKey": "请换成你自己生成的 Reality 私钥",
          "shortIds": [""]
        }
      },
      "sniffing": {
        "enabled": true,
        "destOverride": ["http", "tls"]
      }
    }
  ]
}
```

生成密钥和 UUID 的命令：

```bash
# 生成 Reality 密钥对（Xray 提供 x25519 工具）
xray x25519

# 生成客户端 UUID
cat /proc/sys/kernel/random/uuid

# 私钥填进服务端配置，公钥填进面板的节点配置或订阅信息
# 私钥只留在服务端，不要贴到面板、工单或任何公开地方
```

> 为什么私钥绝不能外泄？Reality 的安全性建立在“只有服务端持有私钥、客户端持有公钥”之上。私钥一旦泄露，别人就能冒充你的服务端做握手，伪装和鉴权同时失效，换私钥等于所有订阅都要重发，得不偿失。

## 两个都上：同一台机器的共存方案

很多新手以为一台机器只能选一个协议，其实完全可以共存，只要端口不冲突。最常见的分法是：

- VLESS Reality 占 TCP 443，走标准 HTTPS 端口，伪装效果最好。
- Hysteria2 占另一个 UDP 端口，例如 8443，避免和 443 抢端口，也便于在防火墙里单独放行。

```bash
# 共存时的端口与防火墙检查清单
# 1. VLESS Reality：TCP 443 入方向放行
# 2. Hysteria2：UDP 8443 入方向放行（注意是 UDP，不是 TCP）
# 3. 面板机到落地机的 API 回连端口按你面板的要求放行，不要和协议端口混淆
# 4. 云厂商安全组和机内防火墙（ufw / firewalld / iptables）两边都要放行，只放一边等于没放

# 以 ufw 为例
ufw allow 443/tcp
ufw allow 8443/udp
ufw status numbered
```

> 为什么 Hysteria2 建议换一个 UDP 端口而不是也抢 443？同一台机器上 TCP 443 和 UDP 443 其实可以共存，但很多面板、反代或证书工具默认会占用 TCP 443，分开端口能减少排查时的干扰，出问题时一眼就能区分是哪个协议的端口。

共存还有一个面板层面的好处：同一个落地机在面板里可以对应两个节点条目，用户订阅里同时拿到两个协议入口。一个协议在某个地区突然不好用时，用户切另一个就能恢复，不用等你半夜起来换节点。

## 验证：上线前必须跑通的三件事

两个协议都配好后，不要直接推给全部用户，先做三轮验证：

```bash
# 第一轮：服务端自查
# 1. Hysteria2：journalctl 看启动日志无报错，ss -ulnp 能看到 UDP 监听
# 2. VLESS Reality：Xray 日志无配置解析报错，ss -tlnp 能看到 TCP 443 监听
# 3. 两边配置文件改完都要重启服务，改配置不重启等于没改

# 第二轮：从外网探测端口
# 1. TCP 443：从另一台机器 telnet 或 curl 目标域名，看 TLS 握手是否正常
# 2. UDP 端口：用支持 QUIC 的客户端实际连一次，只凭端口扫描判断 UDP 通不通不可靠

# 第三轮：分场景实测
# 1. 白天、晚高峰各测一次速度和延迟，不要只测一次就下结论
# 2. Wi-Fi 和移动网络各测一次，移动网络丢包多，Hysteria2 的优势往往在这里体现
# 3. 让身处目标地区的用户实测一次，你本地测得通不代表用户那边通
```

> 为什么 UDP 端口不能只靠扫描判断？很多 UDP 服务对未认证的探测包不回包，扫描结果“关闭”可能是假阴性；只有用真实协议握手一次，才能证明端口、配置、密钥三者同时是对的。

## 常见坑汇总

- **只看跑分选协议**：一次测试、一条线路的结论推到所有用户身上，换个时间、换个地区结论可能反转。
- **Hysteria2 只放行 TCP 端口**：它走 UDP，防火墙只放 TCP 等于没放，连接会直接超时。
- **Reality dest 乱填**：填一个不存在、不支持 TLS 1.3 或与服务器地区不匹配的域名，握手直接失败，还容易暴露异常特征。
- **Reality 私钥外泄或复用**：多台机器共用同一对密钥，一台出问题等于全部出问题，每台落地机单独生成。
- **UUID 或密码用弱口令**：面板里图方便填 `123456` 之类的密码，等于把节点入口敞开，务必用随机强口令。
- **改配置不重启**：Xray、Hysteria2 改完配置都要重启服务才生效，排障时先确认服务真的重载了新配置。
- **共存时端口冲突**：面板反代、证书工具和协议入口抢 443，启动日志报端口占用时先查是谁占了端口再改。
- **只测本地、不测用户侧**：你机器上通不代表目标地区通，上线前一定要有目标地区的实测结果。
- **一个协议出问题就全站换协议**：两个协议共存时，先让用户切另一个入口恢复，再慢慢排障，不要一出问题就推倒重来。
- **证书过期无人管**：Hysteria2 用 ACME 证书时，续期失败会导致握手失败，证书续期要纳入日常巡检。

选协议没有标准答案，只有适合你用户和线路的答案。先按场景定一个主协议，条件允许就两个都上，晚高峰和目标地区实测一轮再全量推——这套流程走下来，事后返工的概率会小得多。

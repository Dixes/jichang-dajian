# Xboard 换域名后订阅全失效：旧域名重定向与订阅迁移实操

换个域名本来是小事，结果一换，用户手里的订阅全断了：客户端拉取订阅报 404 或者证书错误，支付回调也收不到了，群里一下子全是“用不了了”。问题不在换域名这个动作本身，而在于机场的域名散在太多地方：面板地址、订阅链接、节点配置、支付回调地址、反代和证书，每一处都绑着旧域名。只改了面板里的域名就以为换完了，漏掉的那几处会在用户真正使用时逐个爆出来。

换域名要按“先跑通新域名，再迁移旧流量，最后才回收旧域名”这个顺序做。最忌讳的操作是先把旧域名解析删掉、证书吊销、反代配置删掉，再去配新域名——这样旧订阅立刻全断，新订阅又还没跑通，中间没有任何缓冲。正确的做法是新旧并行一段时间：新域名先完整跑通，旧域名保留重定向，确认大部分用户都切过来之后，再考虑停掉旧域名。

## 先想清楚：换域名到底会断掉哪几处

动手之前，先把跟旧域名有关的地方列出来，逐项核对，不要凭感觉改：

- 面板后台地址：管理员登录、用户中心都在这个域名下，改了域名，登录入口就变了。
- 订阅链接：用户客户端里保存的订阅地址一般是 `https://旧域名/api/v1/client/subscribe?token=xxx` 这类形式，域名一换，旧订阅地址就请求不到新面板了。
- 节点配置里的地址：如果节点域名、订阅域名写的是旧域名，客户端按旧地址去拉节点信息也会失败。
- 支付回调地址：支付平台后台登记的回调地址如果还是旧域名，换域名后要么回调不到新面板，要么旧域名一停回调就彻底丢了。
- 反代与证书：Nginx 或 Caddy 上旧域名的反代配置和证书，跟新域名是两套，配新域名时要单独配，不能只改面板里的一个字段。

把这张清单列清楚，换域名就从“改一个地方”变成“逐项迁移”，漏项的概率会小很多。清单上的每一项改完都要单独验证，不要改完所有项才一次性验证——一次性验证出问题时，根本分不清是哪一项改错了。

## 第一步：新域名先跑通，再动旧域名

先给新域名做解析，指向面板机，然后配好反代和证书，确认新域名能正常打开面板、能登录、能拉取订阅，再往下走。旧域名在这一步一个字都不要动。

```bash
# 查新域名解析是不是已经生效，返回的 IP 应该是面板机的 IP
dig +short new.example.com

# 查新域名 HTTPS 是不是通的，证书是不是新域名的、没有过期
curl -I https://new.example.com
```

`dig +short` 返回面板机 IP，说明解析已经生效；如果返回的还是旧 IP 或者解析商的默认地址，说明解析还没生效或者配错了记录，不要急着往下配反代和证书，先等解析生效。`curl -I` 返回 200 并且证书信息是新域名的，说明反代和证书都通了；如果报证书域名不匹配，说明反代上挂的还是旧域名的证书，要单独给新域名申请证书。

反代配置上，新域名要单独写一份 server 块，不要直接把旧域名的 server_name 改成新域名——那样旧域名立刻就没人接管了。新旧两个 server 块并存，新域名走面板，旧域名先保持原样，后面再改成重定向。

```nginx
# 新域名反代面板的示例，换成你自己的面板端口和域名
server {
    listen 443 ssl;
    server_name new.example.com;

    ssl_certificate /etc/letsencrypt/live/new.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/new.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

`proxy_set_header Host $host` 的意思是把客户端请求的域名原样传给面板，面板靠这个域名判断当前站点、生成订阅链接。如果这里写死了旧域名，或者干脆没传 Host，面板生成的订阅链接可能还是旧域名，新域名跑通了，订阅链接却还是旧的，迁移等于没做。改完反代配置要重载，不要只改文件不重载：

```bash
# 检查配置语法，通过后再重载
nginx -t && systemctl reload nginx

# 给新域名申请证书（以 certbot 为例）
certbot --nginx -d new.example.com
```

新域名跑通的标准要具体：浏览器能打开新域名面板并登录、用户中心能正常显示、拿一个测试账号的新订阅链接在客户端能拉取到节点、支付测试能走到回调。这几项都通过，才算新域名真正可用；只打开首页能访问，不算跑通。

## 第二步：面板里把域名、订阅地址、回调地址改齐

新域名通了，再进面板改配置。重点改三处：站点域名、订阅链接生成用的域名、支付回调地址。只改站点域名、不改订阅生成域名，是最常见的漏改——面板能打开，生成的订阅链接却还是旧域名。

```bash
# 先看面板配置文件里还有哪些地方写着旧域名，逐项确认
grep -rn "old.example.com" /opt/xboard/.env /opt/xboard/config/ 2>/dev/null
```

`grep -rn` 是递归搜索旧域名出现的位置，输出的每一行都要看一遍：是站点域名、订阅域名、回调地址，还是日志、注释里顺带提到的旧域名。配置文件里的旧域名要改成新域名，注释和日志里的旧域名不用急着改，改配置时别把注释当成配置一起改错。改完面板配置要重启面板服务或重载配置，只改文件不重启，跑的还是旧配置。

支付平台那边也要同步改：到支付平台后台，把回调地址、通知地址从旧域名改成新域名，改完用一笔小额测试订单验证回调能不能到新面板。回调地址改错、支付平台后台没保存、旧域名回调还在用，这三种情况的表现很像，都是“付了钱订单没变”，要到支付平台后台确认登记的地址确实已经是新域名，而不是只在面板这边改完就以为完事了。

如果面板用了 Cloudflare 代理新域名，还要注意橙云和灰云的区别：橙云走 Cloudflare 代理，灰云是直接解析到源站，两种模式下订阅拉取、回调到达的表现可能不一样，排查时可以先对照这篇说明：[Cloudflare 橙云和灰云对节点有什么影响](guides/cloudflare-orange-vs-grey.md)。换域名期间先不要同时改代理模式，域名和代理模式一起变，出问题时分不清是哪一个改动引起的。

## 第三步：旧域名做 301，不要直接关解析

新域名跑通、面板配置改齐之后，处理旧域名。正确做法是给旧域名做 301 永久重定向到新域名，而不是直接删解析、停反代。客户端拉旧订阅地址时，301 会把请求带到新域名对应路径上，老用户不用手动换订阅就能继续用；直接删解析，老用户手里的订阅地址立刻变成死地址，只能一个个通知他们手动更换。

```nginx
# 旧域名 301 到新域名的示例：保留请求路径，只换域名
server {
    listen 443 ssl;
    server_name old.example.com;

    ssl_certificate /etc/letsencrypt/live/old.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/old.example.com/privkey.pem;

    return 301 https://new.example.com$request_uri;
}
```

`return 301 https://new.example.com$request_uri` 的意思是：所有打到旧域名的请求，都永久重定向到新域名下相同的路径。保留 `$request_uri` 很关键，丢掉它，旧订阅地址重定向后就变成了新域名首页，客户端拉到的不是订阅内容，而是首页 HTML，订阅还是断的。旧域名的证书也要保留到重定向生效期间，证书一过期，HTTPS 的旧订阅请求在重定向之前就先报证书错误，根本走不到 301。

重定向配好之后要实测，不要只看浏览器打开旧域名跳不跳转。订阅地址的验证要用 `curl` 跟着重定向走一遍：

```bash
# 跟随重定向拉一次旧订阅地址，看最终是不是新域名的订阅内容
curl -L -s https://old.example.com/api/v1/client/subscribe?token=TEST_TOKEN | head -c 500

# 只看响应头，确认旧域名返回的是 301、Location 指向新域名
curl -I https://old.example.com/api/v1/client/subscribe?token=TEST_TOKEN
```

`curl -L` 是跟随重定向，输出订阅内容才算重定向链路通了；如果输出的是首页 HTML，说明重定向丢了路径，要回去检查 `$request_uri` 有没有保留。`curl -I` 看到 301 和指向新域名的 Location，说明旧域名这一层没问题；如果返回 404，说明旧域名的反代配置已经被删掉或者被别的 server 块抢占了，要先恢复旧域名的 server 块。

旧域名重定向要保留一段时间，不要新域名一跑通就立刻停掉。用户客户端的订阅更新有缓存周期，有的人几天才更新一次订阅，旧域名停得太早，这部分用户还没切过来就断了。保留多久看用户规模和订阅更新频率，一般至少保留一个完整的订阅更新周期，确认旧域名的访问量降到很低之后，再考虑停掉。

## 第四步：节点端、订阅端逐个验证

域名换完、重定向配好，最后要按用户真实使用的链路逐个验证，而不是只在面板后台点几下：

```bash
# 1. 新订阅链接在客户端能拉取到节点，节点数量和之前一致
# 2. 旧订阅链接经 301 跳转后也能拉取到同样的节点列表
# 3. 一笔小额测试订单支付成功后，面板订单状态能自动变更
# 4. 面板后台、用户中心、订阅页面在新域名下都能正常打开
```

验证时要分账号、分场景：新注册账号拿新订阅链接、老账号用旧订阅链接、已经过期的账号续费走新回调地址，这几种情况都要走一遍。只验证管理员自己的账号，很容易漏掉老用户旧订阅、支付回调这类管理员平时不走的路径。验证通过之后，把旧域名重定向的访问日志留几天，观察还有多少请求走旧域名、是不是都正常跳转了，再决定旧域名什么时候停。

## 常见坑

- **先删旧解析再配新域名**：旧订阅立刻全断，新域名还没跑通，中间没有任何缓冲，正确顺序是新旧并行。
- **只改面板域名，不改订阅生成域名**：面板能打开，生成的订阅链接还是旧域名，用户拿到的还是旧地址。
- **支付回调地址没同步改**：面板换了域名，支付平台后台登记的还是旧域名，回调不到新面板，订单卡在待支付。
- **旧域名直接删反代**：客户端拉旧订阅直接 404，应该先做 301，把旧订阅请求带到新域名。
- **301 丢了请求路径**：重定向到新域名首页，客户端拉到的是首页 HTML，不是订阅内容，一定要保留 `$request_uri`。
- **旧域名证书提前过期**：HTTPS 请求在重定向之前就报证书错误，旧域名证书要保留到重定向期结束。
- **反代 Host 写死旧域名**：面板按 Host 生成订阅链接，Host 写死了，订阅链接永远是旧域名。
- **改了配置不重启服务**：面板、反代改完文件没重载，跑的还是旧配置，验证时看到的还是旧行为。
- **域名和代理模式一起改**：换域名期间又改 Cloudflare 橙云灰云，出问题分不清是哪一处引起的，分开改、分开验证。
- **只验证管理员账号**：老用户旧订阅、续费回调这些路径管理员平时不走，不逐个验证就会漏掉。
- **旧域名停得太早**：用户订阅更新有缓存周期，旧域名至少保留一个完整更新周期，等旧域名访问量降下来再停。
- **新域名只验证首页能打开**：首页能打开不等于订阅能拉取、支付回调能到，新域名要按完整链路验证。

# 面板公告与工单功能怎么用

机场跑起来之后，真正花时间的往往不是装节点，而是每天应付用户：套餐到期了没人知道、节点挂了用户到处问、支付出了问题找不到人。面板自带的「公告」和「工单」就是干这个的：公告负责把一件事一次性告诉所有人，工单负责把一个用户的问题变成可跟踪的任务。这篇以 Xboard 为例，讲清楚两个功能怎么开、怎么写、出了问题怎么查。

## 公告：先说清楚，再发出去

### 公告放在哪里、用户在哪里看到

Xboard 的公告入口一般在管理后台的「公告/通知」一栏（不同版本叫法略有差异，有的叫「公告管理」），前台则显示在用户中心的首页顶部或登录后的弹窗里。发之前先确认一件事：你的面板域名能正常打开、用户登录后确实能看到公告位。如果公告位本身没启用，写得再好也没人看。

### 公告分几类，分别什么时候用

不要把所有消息都写成同一类公告，用户看多了就不看了。建议只用三类：

- **维护通知**：节点维护、面板升级、支付通道切换，提前发，写明影响范围和预计恢复时间。
- **规则说明**：套餐规则、设备数限制、禁止用途，长期置顶，偶尔更新。
- **故障通报**：节点突然不可用、订阅大面积异常，事发后尽快发，先承认问题再给时间表。

维护通知和故障通报要分开写：前者是「计划内」，后者是「计划外」，混在一起用户会分不清你到底靠不靠谱。

### 一则合格公告的写法

写公告有个固定结构，照着填就行：

```markdown
10 月 28 日凌晨节点维护

影响范围：日本、香港节点
维护时间：10 月 28 日 02:00–04:00（UTC+8）
维护内容：落地机系统更新与线路调整
维护期间：上述节点可能短暂不可用，其他节点不受影响
恢复后：无需任何操作，订阅会自动恢复
```

要点就四个：影响谁、什么时候、会发生什么、用户要不要做什么。最后一句最重要——凡是用户不需要操作的，一定要明说「无需操作」，否则维护期间工单会被「我需要做什么」淹没。

### 公告的常见坑

- **只写在群里不写在面板**：用户不一定在群里，面板公告才是所有人登录后都能看到的地方。
- **故障通报没有后续**：发了「正在处理」之后，修好了一定要再发一条「已恢复」，否则用户会默认问题还在。
- **公告长期不更新**：置顶的维护通知过了三个月还在，等于告诉用户这个面板没人管。维护结束就撤下或改为已完成状态。
- **用公告发促销**：公告位是信任资产，塞满促销信息会让真正重要的维护通知也被忽略。促销放首页横幅或套餐页，别占公告位。

## 工单：把问题变成可跟踪的任务

### 工单处理的基本流程

用户在前台提交工单 → 后台按类别分流 → 管理员回复 → 用户确认解决 → 关闭。一个工单从提交到关闭应该全程留在系统里，不要把处理过程挪到私聊——私聊处理的问题无法复盘，同一个问题下次还得重新问一遍。

### 工单分类先定好，别让用户自由发挥

工单类别建议一开始就定死四类，多了没人选、少了分不清：

| 类别 | 典型问题 | 处理优先级 |
| --- | --- | --- |
| 账号与套餐 | 套餐没到账、到期时间不对 | 高 |
| 订阅与连接 | 订阅更新失败、节点连不上 | 高 |
| 支付问题 | 付款成功未到账、订单号查询 | 高 |
| 其他建议 | 线路建议、功能反馈 | 低 |

分类的意义是分流：支付问题要先查订单和支付回调，连接问题要先查节点状态，两类问题的排查路径完全不同。分错类等于白问一轮。

### 回复工单的标准动作

收到工单先别急着回复，先做三件事：

1. **看用户基本信息**：套餐、到期时间、最近登录 IP 是否异常，判断是账号问题还是普遍问题。
2. **看同类工单**：同一时间段有没有多个用户报同一个节点的问题——有，就是节点故障，先发故障公告再逐一回复，比一个个解释省事得多。
3. **复现或查日志**：连接问题查节点端和面板的日志，支付问题查订单状态和支付网关回调记录（支付回调验签失败的排查见本仓库的[易支付对接常见坑：异步通知验签失败](epay-notify-sign.md)）。

回复时照这个结构写：

```markdown
已收到，正在处理：

1. 已确认您的订单状态：[已支付 / 未到账 / 回调异常]
2. 处理进度：[已联系支付方核查 / 已手动补发套餐 / 节点已恢复]
3. 您需要做的事：[无需操作 / 请重新更新一次订阅 / 请提供订单号后 6 位]

预计解决时间：今天 20:00 前
```

给用户一个明确的时间预期，比「尽快处理」管用得多。超时了没解决也要回一条，告诉用户进展卡在哪里。

### 工单积压了怎么办

工单越积越多通常不是人手问题，而是三个地方没做好：

- **没有公告**：同一个故障几十个人各开一单，先发故障公告，再在公告里写「已知问题，正在处理，无需重复提交」。
- **没有常见问题页**：订阅更新失败、设备数超限这类每周都出现的问题，写成一篇帮助文档，工单回复里直接贴链接。
- **没有关闭机制**：用户问题解决后不关闭工单，列表里永远一堆「处理中」。解决后请用户确认，无回复超过 3 天的按「已解决」关闭，并在回复里写明「如仍有问题请重新开启本单」。

## 两个功能联动的日常节奏

公告和工单不是两个孤立功能，日常运营里它们是这样配合的：

1. **维护前一天**：发维护公告，写明影响范围和时间。
2. **维护期间**：故障类工单统一回复「已知维护，公告中有时间表」，不逐一解释。
3. **维护结束**：发恢复公告，把维护期间积压的工单批量关闭并附恢复说明。
4. **每周复盘**：看一眼本周工单最多的类别——连接问题最多，说明节点或订阅环节有隐患；支付问题最多，说明支付回调或到账流程要修。

坚持一个月，工单量会明显下降：不是用户没问题了，而是大部分问题在变成工单之前，已经被公告和帮助文档挡住了。

## 排障：公告或工单本身出问题

- **公告发了用户看不到**：先检查公告是否设了可见范围或生效时间，有的面板支持按用户组推送，误设成某个分组会导致大部分用户看不到；再检查前台模板是否把公告位渲染出来了。
- **工单提交后后台收不到**：检查面板的邮件/通知配置——很多面板靠邮件提醒管理员新工单，邮件发不出去等于工单石沉大海；同时确认数据库中工单表写入正常。
- **工单回复用户收不到**：同样先查邮件配置，再看用户填的邮箱是否正确。工单系统依赖邮件提醒，邮件通道挂了，整个工单流转就断了。

归根结底，公告和工单都是「把信息送到对的人手里」的工具：公告是广播，工单是点对点。广播不到位，点对点就会被淹没；点对点没有闭环，广播的信任也会被耗尽。两个都跑顺了，机场的日常运营才算真正立起来。

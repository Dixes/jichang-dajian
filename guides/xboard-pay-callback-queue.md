# Xboard 支付回调后订单仍显示待支付：队列与定时任务排查

用户已经付完钱，支付平台那边订单是成功的，回到 Xboard 面板一看，订单却还卡在“待支付”，订阅也没开通。很多人第一反应是支付接口坏了，或者去改订单状态手动放行。其实这类问题常常不在支付那一环，而在回调之后：支付平台把“已支付”通知发过来了，面板收到了、验签也通过了，但真正把订单改成已支付、给用户开通订阅的那一步，是交给队列任务或定时任务去做的。队列没跑、定时任务没配、任务失败了没人重试，订单就会一直卡在待支付——钱收了，服务没开，用户来投诉，管理员还查不到错在哪。

先把责任分清楚：支付回调只负责“告诉面板钱到了”，订单状态变更和订阅开通是面板内部的后续动作。回调日志正常，不等于开通逻辑跑完了；订单还是待支付，也不等于支付失败。按“回调到了没有 → 队列跑了没有 → 定时任务配了没有 → 失败任务怎么补”这个顺序查，比一上来就重启面板、重配支付要快得多。

## 先定性：确认支付平台那边的订单到底是什么状态

动手之前，先到支付平台后台查这笔订单：是已支付，还是根本没支付成功。如果支付平台那边也是待支付或已关闭，那问题在用户支付环节，跟面板队列无关，不要往队列方向查。

```bash
# 先看面板机上最近的支付相关日志，确认回调请求有没有打进来
# 下面是常见路径示例，换成你自己的面板日志路径再查
tail -n 300 /var/log/nginx/access.log | grep -iE 'notify|callback|pay'
```

如果日志里根本找不到支付平台的回调请求，先查支付平台后台配置的回调地址对不对、面板域名能不能从外网访问、反代有没有把回调请求拦掉。回调地址填错、域名解析不对、Cloudflare 或防火墙把回调挡在外面，面板收不到通知，自然不会改状态——这属于回调没到，不是队列问题。

如果回调请求到了，但验签失败被面板拒绝了，那也要先按验签方向查：[易支付对接常见坑：异步通知验签失败](guides/epay-notify-sign.md)。验签失败的回调会被面板直接丢掉，不会进入后续的订单处理流程，队列里当然也不会有对应的开通任务。验签通过、回调日志正常，订单却还是待支付，才能锁定在队列和定时任务上，往下查。

还有一点要先区分：是只有这一笔订单卡住了，还是所有支付订单都卡住了。只卡一笔，多半是这笔任务失败了或被异常数据卡住了；所有订单都卡住，多半是队列服务根本没跑，或者定时任务根本没配。单笔问题按单笔的任务去查，全量问题先查服务和调度配置，不要把全量问题当成单笔问题去逐笔补单。

## 第一步：确认回调之后有没有产生待处理的任务

Xboard 这类面板通常不会在收到回调的请求里直接改订单、开通订阅，而是把“处理支付成功”这件事写成一个任务，交给队列去异步执行。这样做的好处是回调响应快，不会因为开通逻辑慢而让支付平台以为通知失败、反复重发；代价就是队列一停，订单状态就停在原地。

先看队列相关的服务和进程在不在跑。不同部署方式的服务名不一样，下面以常见的 Supervisor / systemd 托管为例，换成你自己的实际服务名：

```bash
# 看队列 worker 是不是在跑（Supervisor 托管的常见写法）
supervisorctl status

# 如果是 systemd 托管的队列服务，看它的状态
systemctl status xboard-queue --no-pager

# 看队列里是不是积压了一大堆没处理的任务
# 具体命令取决于你用的队列驱动（数据库 / Redis），先确认驱动再查
ps aux | grep -iE 'queue|worker' | grep -v grep
```

如果 `supervisorctl status` 里队列 worker 显示 `STOPPED`、`FATAL` 或 `EXITED`，那就是队列根本没在干活，回调进来也只会排队等着，不会有人去改订单状态。这时先看 worker 的错误日志，确认是配置错了、依赖没装，还是启动后立刻崩了，再针对性修，不要只重启一次就了事——配置错误导致的崩溃，重启多少次还是会崩。

如果 worker 在跑、但任务积压越来越多，说明处理速度跟不上，或者处理任务时一直在报错重试。看一下 worker 日志里最近的报错：是数据库连不上、是某个任务抛异常，还是任务处理超时被反复重试。任务一直失败重试还会拖慢整个队列，让后面正常的订单也跟着卡住，这种情况下要先把失败的任务找出来，而不是一味加 worker 数量。

## 第二步：查队列 worker 的配置——跑在哪个环境、连的哪个库

队列 worker 没跑起来，或者跑起来却处理不了任务，常见原因出在配置上：worker 读的环境变量和 Web 服务不一致、连的数据库或 Redis 不是同一个、队列名写错了。Web 服务把任务写进了 A 队列，worker 却在监听 B 队列，两边永远对不上，任务就永远没人处理。

```bash
# 对照 Web 服务和 worker 的环境配置，重点看数据库、Redis、队列名这几项
cat /opt/xboard/.env | grep -iE 'DB_|REDIS|QUEUE'

# 看 worker 的启动配置，确认它监听的队列和运行的用户
cat /etc/supervisor/conf.d/xboard-queue.conf
```

`DB_HOST`、`DB_DATABASE`、`REDIS_HOST`、`QUEUE_CONNECTION` 这类配置的意思是：面板用哪个数据库、哪个 Redis、哪种队列驱动。Web 服务和 worker 必须指向同一个数据库和同一个 Redis，否则 Web 服务写下的任务 worker 根本看不到；队列名也一样，写任务和取任务的队列名不一致，任务就会一直躺在没人监听的队列里。改配置之前先把两边的配置并排对照，改完 worker 配置要重启 worker 才能生效，只改文件不重启，旧配置还在跑。

还有一个容易被忽略的点：worker 运行的用户权限。如果 worker 是用普通用户跑的，而面板文件、日志目录只有 root 可写，任务处理到写日志、写缓存那一步就会失败。看 worker 日志里有没有 `permission denied` 之类的报错，有的话先把目录权限或运行用户对齐，不要直接给 777 了事——权限放得过大，面板安全上会留下口子。

## 第三步：查定时任务——队列之外的那条“兜底线”

有些面板除了队列 worker，还会靠定时任务（cron）去做两件事：一是定期扫描待支付订单、向支付平台查询订单状态并补单；二是定期执行订阅到期、流量重置这类调度任务。如果队列 worker 挂了，定时补单任务还能把卡住的订单捞回来；如果定时任务也没配，那队列一停就没有任何兜底，订单卡多久都没人管。

```bash
# 看当前用户的定时任务里有没有面板相关的调度任务
crontab -l

# 看系统级的定时任务目录里有没有面板调度
ls -la /etc/cron.d/ | grep -i xboard

# 常见的 Laravel 调度写法：每分钟跑一次调度器，由调度器再分发具体任务
# * * * * * cd /opt/xboard && php artisan schedule:run >> /dev/null 2>&1
```

`schedule:run` 的意思是 Laravel 的调度入口：每分钟被 cron 调用一次，再由它决定这一分钟该跑哪些任务。cron 里没有这一行，调度器永远不会被触发，依赖调度的补单、到期处理、流量统计都不会跑。反过来，cron 里有这一行，但面板代码里的调度任务本身被注释掉或配错了时间，也一样不会跑——要两边都确认：cron 调度入口在不在，面板里的具体调度任务配没配。

定时任务的日志也要看一眼。`schedule:run` 默认输出经常被重定向到 `/dev/null`，出问题时什么痕迹都留不下。排查期间可以先把输出改到一个临时日志文件，跑几个周期看调度器到底执行了哪些任务、有没有报错，定位清楚再改回原来的重定向方式。

```bash
# 排查期间临时把调度输出写到日志文件，观察几个周期
# * * * * * cd /opt/xboard && php artisan schedule:run >> /tmp/xboard-schedule.log 2>&1

# 看调度日志里有没有报错或异常
tail -n 200 /tmp/xboard-schedule.log
```

## 第四步：确认卡住的订单怎么补——先查任务，再手动补单

定位到是队列问题还是定时问题之后，卡住的订单要处理，但处理顺序有讲究：先确认这笔订单在支付平台确实已支付，再补单；先查失败任务的报错原因，再重跑任务。没确认支付状态就直接把订单改成已支付、给用户开通订阅，万一用户其实没付成功，就是白送服务；没查清失败原因就直接重跑任务，任务可能还是会失败，或者重复执行导致重复开通。

```bash
# 先到支付平台后台核对这笔订单号的支付状态，确认已支付再往下走
# 再看队列失败任务表 / 失败日志里有没有这笔订单对应的任务记录
# 下面是数据库队列的常见排查思路，表名换成你自己的实际表名
mysql -u root -p -e "SELECT * FROM failed_jobs ORDER BY failed_at DESC LIMIT 20;"
```

`failed_jobs` 是 Laravel 队列默认的失败任务表，记录的是处理失败后不再自动重试的任务。里面有记录，说明任务确实被执行过、但执行时抛了异常，异常信息就写在记录里，顺着异常信息修代码或数据问题，再重跑任务。里面没有记录，说明任务可能还在排队没被执行（worker 没跑或队列名不对），或者任务根本没被写进队列（回调处理逻辑在写任务之前就出错了），要回到第一步和第二步重新确认。

补单的操作本身要谨慎：优先用面板自带的“查询订单状态”“重新回调”“补单”功能（如果有的话），而不是直接改数据库。直接改数据库改订单状态很容易漏掉关联动作——只改了订单状态、没开通订阅，用户还是用不了；只开通了订阅、没改订单状态，对账时又会对不上。面板自带的补单流程一般会把改状态、开通订阅、写日志这几步一起走完，比手动改库稳妥。如果面板没有补单功能，手动处理时也要把订单状态、订阅开通时间、用户流量额度这几项一起核对，不要只改其中一项。

## 第五步：验证——新订单能自动开通，旧订单不再复发

修完队列或定时任务，不要只看卡住的那一笔订单变了状态就收工，要验证两件事：新支付的订单能不能自动走完流程，之前卡住的原因会不会复发。

```bash
# 1. 确认队列 worker 和调度任务都在跑
supervisorctl status
crontab -l | grep -i xboard

# 2. 用一笔小额测试订单走一遍完整支付流程，确认订单自动变成已支付、订阅自动开通
# 3. 观察队列积压是否在下降，而不是越积越多
ps aux | grep -iE 'queue|worker' | grep -v grep
```

第 2 项最好用真实的小额支付走一遍，而不是只在后台点一下“补单”：补单成功只证明手动流程能走通，自动流程（回调 → 队列 → 改状态 → 开通）有没有恢复，必须靠一笔新订单来验证。验证时顺带确认：用户端订阅链接能正常拉取、流量额度是对的、订单列表里的状态和支付平台后台一致，这几项都对了，才算真正修好。

验证通过之后，把排查期间临时改过的东西收回来：临时日志文件的重定向改回原来的方式、临时放宽的权限收紧、测试订单按财务流程处理。排查用的临时改动留在生产环境里，本身就是下一个故障的隐患。

## 常见坑

- **回调到了就以为订单该变了**：回调只是通知，改状态和开通订阅是队列或定时任务做的，回调日志正常不等于后续流程跑完了。
- **验签失败和队列问题混在一起查**：验签失败的回调会被直接丢掉，根本进不了队列，先按验签查，验签通过再查队列。
- **只重启面板，不看队列 worker**：Web 服务重启了，队列 worker 不一定跟着重启，worker 停着，订单还是不会自动开通。
- **Web 和 worker 配置不一致**：数据库、Redis、队列名两边指向不同地方，任务写进了没人监听的队列，永远没人处理。
- **改了 worker 配置不重启**：配置文件改了、worker 还在跑旧配置，验证时看到的还是旧行为。
- **没有定时补单兜底**：只靠队列一条线，队列一停就没有任何补救，定时查询订单状态的兜底任务要配上。
- **cron 调度入口缺失**：面板里的调度任务配得再全，cron 里没有每分钟调用调度器那一行，也一个都不会跑。
- **没确认支付状态就手动改库**：用户其实没付成功却被手动开通，等于白送服务；只改订单状态不改订阅，等于没修好。
- **失败任务不看异常就重跑**：失败原因没修，重跑还是会失败，还可能重复执行、重复开通。
- **临时排查改动留在生产环境**：临时日志、临时权限、临时放宽的配置不收回来，会成为下一个故障的隐患。
- **只看一笔订单，不看全量**：单笔卡住和全量卡住的根因不一样，全量卡住要先查服务和调度，不要逐笔补单掩盖全量问题。

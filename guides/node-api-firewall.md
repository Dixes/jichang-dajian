# 节点端 API 防护：只允许面板 IP 访问

节点端为了让面板管理它，通常会开一个 API 端口：面板通过它下发配置、拉取状态，节点端通过它上报流量和在线情况。这个端口一旦对全网开放，就等于把节点的管理入口摆在了公网上——扫描器每天都在扫这类端口，撞上弱口令、旧版本漏洞或配置失误，就可能被接管、被改配置、被拿去跑别人的流量。本篇讲怎么把这个口子收紧到只允许面板机 IP 访问，顺带把配套的检查做全。

## 先确认你要护住的是哪个端口

动手之前先别急着加规则，把三件事对清楚，否则规则加错地方，面板推不动配置，节点反而离线。

第一，确认节点端 API 到底监听在哪个端口。不同节点端和版本默认值不一样，有的和协议端口分开，有的默认只监听本地回环。先在落地机上查：

```bash
# 看节点端进程实际在监听哪些端口
ss -tlnp | grep -E "v2bx|xray|sing-box"

# 再看配置文件里 API 相关的端口字段，确认是不是下面这个端口
grep -n -i "api" /etc/v2bx/config.yaml
```

第二，确认调用方是谁。正常情况下，节点端 API 的调用方只有一个：你的面板机。如果还有监控脚本、其他中转机在调它，先把它们的 IP 也列进白名单，不要事后靠放宽规则来救火。

第三，确认面板机 IP 是固定的。面板机如果是按量计费、经常重建的机器，IP 一变规则就失效。面板机尽量用固定 IP，实在不行也要把“面板换 IP 后同步改防火墙”写进自己的迁移清单。

把这三项记成一张小表，后面所有规则都按它填：

```text
落地机 IP：198.51.100.20
节点端 API 端口：6688（示例，按实际改）
面板机 IP：203.0.113.10（唯一调用方）
```

这一步和面板机、落地机分离部署的思路是一脉相承的：角色分清楚，防护才有边界，分离部署的分工细节见本仓库的[面板机与落地机分离部署注意事项](panel-node-separation.md)。

## 第一步：机内防火墙只放行面板机 IP

最直接的做法是在落地机上用机内防火墙收口。以 UFW 为例，顺序很重要：先放行 SSH 和协议端口，再给 API 端口加来源限制，最后才启用默认拒绝，不然一个手滑就把自己的 SSH 断掉。

```bash
# 先放行 SSH，保住当前会话；协议端口按面板里该节点的实际配置改
ufw allow 22/tcp
ufw allow 443/tcp

# 关键规则：节点端 API 端口 6688，只允许面板机 203.0.113.10 访问
ufw allow from 203.0.113.10 to any port 6688 proto tcp

# 确认规则无误后再启用；如果 UFW 已启用，这一步会提示，直接回车即可
ufw enable
ufw status numbered
```

> 为什么是“只允许面板机 IP”，而不是“加个复杂密码就行”？密码防的是猜中，来源限制防的是根本够不着。两者都要有，但来源限制是第一道门：扫描器连握手都完成不了，后续的漏洞利用也就无从谈起。

如果你用的是 firewalld，逻辑完全一样，只是写法不同：

```bash
# firewalld：把 API 端口从公开服务里拿掉，改用富规则只放行面板机 IP
firewall-cmd --permanent --remove-port=6688/tcp
firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="203.0.113.10" port port="6688" protocol="tcp" accept'
firewall-cmd --reload
firewall-cmd --list-all
```

注意：机内防火墙和云厂商安全组是两层，不要只做一层就以为完事。下一节讲安全组那层怎么配。

## 第二步：云厂商安全组再收一层

很多 VPS 在机房入口还有一层安全组，机内防火墙配得再严，安全组里 API 端口对 `0.0.0.0/0` 开放，流量照样能打到机器上。两层要保持一致：

- 安全组里给节点端 API 端口加一条规则：协议 TCP，端口 6688，来源只填面板机 IP `203.0.113.10/32`。
- 不要图省事写成 `0.0.0.0/0`，也不要写成面板机所在的整个网段——网段里其他机器并不需要调这个接口。
- 协议端口（例如 443）保持对用户开放，面板网站和订阅地址也要对用户开放，只有节点端 API 端口是“仅面板机可见”的特例。

> 为什么要两层都配？机内防火墙是最后一道，安全组是第一道。万一哪天重装系统、防火墙规则丢了，安全组还能顶住；万一安全组被别人改错，机内防火墙还能顶住。单点配置总有丢的时候，双层是给失误留余地。

面板机如果换了 IP，两层规则要一起改，只改一层会出现很迷惑的现象：面板后台时好时坏，或者从面板机测能通、从别处测也能通——后者说明还有一层没收紧。

## 第三步：API 自身的认证也别省

来源限制不是万能的：面板机本身被入侵、IP 被 spoof（内网场景）时，来源限制就拦不住了。所以 API 自身的认证也要配好，两者叠加才算完整。

```bash
# 检查节点端配置里的认证项是否都填了，不要留空、不要用默认值
grep -n -E "ApiKey|Token|Secret" /etc/v2bx/config.yaml

# 密钥生成：用系统随机数现生成，不要用 123456、面板域名这类可猜的值
openssl rand -hex 16
```

三条硬性要求：密钥和面板后台该节点配置的密钥逐字一致，错一位面板就会认证失败；密钥只存在面板后台和落地机配置文件里，不要写进公开的教程、截图或聊天记录；换过密钥后要重启节点端进程，让新密钥生效，顺带确认面板后台节点状态恢复在线。

另外，节点端 API 尽量不要和面板网站共用同一个域名和证书路径。API 走自己的端口和内部认证，面板网站走 Nginx 或 Caddy 的反代和证书，两边混在一起，改一处就容易牵连另一处。

## 第四步：验证防护真的生效了

规则加完不能凭感觉收工，要从三个方向各测一次，确认“该通的通、不该通的不通”：

```bash
# 1. 从面板机测：应当能通（面板机 IP 在白名单里）
#    在面板机 203.0.113.10 上执行
curl -s -o /dev/null -w "%{http_code}\n" http://198.51.100.20:6688/ --max-time 10

# 2. 从任意非面板机测：应当不通，连接超时或被拒绝
#    在一台与面板机无关的机器上执行，返回超时即规则生效
curl -v http://198.51.100.20:6688/ --max-time 10

# 3. 面板后台验证：节点状态显示在线，且改一次节点配置能正常下发
#    在面板后台改动该节点的备注或倍率，保存后看落地机日志有没有收到新配置
journalctl -u v2bx -n 30 --no-pager
```

三项里任何一项不符合预期，先别急着放宽规则：面板机不通先查白名单 IP 有没有填错、面板机 IP 是不是变了；非面板机也能通先查安全组那层是不是还开着 `0.0.0.0/0`；面板后台离线先查密钥和节点 ID 有没有抄错。定位顺序是：先看规则，再看认证，最后看日志。

## 常见坑

1. **先启用默认拒绝，后放行 SSH**：UFW 一启用就把自己踢下线。顺序永远是先放行 SSH，再加其他规则，最后启用。
2. **安全组写了 `0.0.0.0/0`**：机内防火墙配得再严，入口那层没收紧等于没做。两层规则逐项核对。
3. **白名单填了域名而不是 IP**：防火墙规则认的是 IP，面板域名解析变了规则不会跟着变。填固定 IP，换 IP 时同步改规则。
4. **面板机换 IP 后忘了改规则**：节点突然离线，面板后台怎么重启都没用。换 IP 时把两层防火墙规则列进迁移清单。
5. **只做了来源限制，没配密钥**：来源限制是第一道门，密钥是第二道门，两道都要有，缺一道都不算做完。
6. **API 端口和协议端口混淆**：把 443 也收成仅面板机可见，用户就连不上节点了。收紧的只是 API 端口，协议端口保持对用户开放。
7. **只测了面板机能通**：没从非面板机测“不通”，就等于没验证防护。三个方向的测试缺一不可。
8. **规则改完不留记录**：过两个月自己都忘了哪个端口是干嘛的。把面板机 IP、API 端口、两层规则截图或记下来，扩第二台落地机时照抄。

节点端 API 防护说穿了就一句话：调用方只有一个面板机，那就只让这一个 IP 够得着它。机内防火墙、安全组、API 密钥三层做齐，再从三个方向测一遍，扫描器扫到这个端口也只能吃闭门羹。之后每扩一台落地机，都按这张小表复制一遍规则，防护就不会随着规模扩大而漏掉。

# Hysteria2 端口跳跃（Port Hopping）配置

Hysteria2 默认只监听一个 UDP 端口（通常是 443）。单端口 UDP 有个天然弱点：针对单个 UDP 端口做限速或封锁，成本很低——运营商 QoS 掐住你这一个端口，整台节点就慢到没法用。端口跳跃（Port Hopping）就是对付这个的：让服务端"看起来"在监听一整段 UDP 端口，客户端每隔一段时间随机换一个端口连接，掐单端口的手段就失效了。

> 前置：本文假设你已经有一台跑起来的 Hysteria2 节点。如果还没搭，先看本仓库的 [Hysteria2 节点搭建与调优](hysteria2-server-setup.md)，把基础节点跑通再来加跳跃。

## 为什么要做端口跳跃：先理解原理

端口跳跃不是什么黑魔法，原理一句话：**服务端只真正监听端口段里的第一个端口，其余端口的流量由防火墙自动重定向过去；客户端则按固定间隔随机换端口发起连接。**

具体到 Hysteria2 的实现：

1. 服务端配置 `listen: :20000-50000` 后，Hysteria2 只在 20000 上真正监听，同时自动建好防火墙规则，把 20001–50000 的 UDP 流量重定向到 20000；
2. 客户端配置里服务器地址写成端口段 `你的域名:20000-50000`，并设置 `hopInterval: 30s`，客户端就每 30 秒随机换一个段内端口；
3. QUIC 是面向连接但底层无连接的协议，换端口对已建立的会话影响很小，用户侧基本无感。

> 为什么跳跃能对抗单端口限速？因为限速/QoS 规则通常是按"目标端口"匹配的。你的流量分散在几万个端口上，对方要么放行、要么把整个 UDP 端口段全掐掉——后者的误伤太大，现实中很少这么干。

## 服务端：一行配置开启端口段监听

Hysteria2 官方原生支持端口段监听（注意：仅 Linux），改一行配置即可。找到你的服务端配置文件（通常是 `/etc/hysteria/config.yaml`），把 `listen` 改成端口段：

```yaml
listen: :20000-50000
```

就这么简单。Hysteria2 启动时会自动用 nftables 或 iptables 建好重定向规则，进程退出时自动清理，不用你手写防火墙规则。

三个前提条件，缺一不可：

- **Linux 系统**：这是官方明确限制的，端口段监听只在 Linux 上支持；
- **装了 nft 或 iptables**：Hysteria2 靠它们建重定向规则，`which nft iptables` 确认至少有一个存在；
- **以 root 运行（或有 CAP_NET_ADMIN 权限）**：改防火墙规则需要权限，普通用户启动会静默失败——表现为只有第一个端口能通。

> 为什么是 root/CAP_NET_ADMIN？因为端口段监听的本质是让 Hysteria2 进程去改系统防火墙表，这属于特权操作。权限不够时它不会报错退出，而是退化成只监听第一个端口，跳跃名存实亡——这是最常见的"配了没效果"原因。

**端口段怎么选**：避开 1–1024 的常用端口和你机器上已有的 UDP 服务端口（先 `ss -ulnp` 看一遍）；段长度 2–5 万是常用值，比如 `20000-50000`；段太长没有额外收益，反而让客户端遍历更慢。

改完重启 Hysteria2：

```bash
systemctl restart hysteria-server
systemctl status hysteria-server --no-pager | head -20
```

### 备选方案：手动 iptables 转发（任何部署方式通用）

如果你的 Hysteria2 是面板下发的配置、改不了 `listen`，或者跑在 Docker 里加权限麻烦，可以用手动 iptables 方案达到同样效果——Hysteria2 本体只监听 443，防火墙把端口段转过去：

```bash
# IPv4：把 20000-50000 的 UDP 转到本机 443（Hysteria2 实际监听端口）
iptables -t nat -A PREROUTING -i eth0 -p udp --dport 20000:50000 -j DNAT --to-destination :443
# IPv6 同理
ip6tables -t nat -A PREROUTING -i eth0 -p udp --dport 20000:50000 -j DNAT --to-destination :443
```

> 为什么用 DNAT `--to-destination :443`？因为目标就是本机，只改端口不改 IP，所以 `:443` 前面留空。`eth0` 换成你的实际出网网卡名，用 `ip route get 1.1.1.1` 看。

规则建完必须做**持久化**，否则重启机器就丢了（这是手动方案最高频的坑）：

```bash
# Debian / Ubuntu
apt install -y iptables-persistent
netfilter-persistent save
```

另外别忘了云厂商的安全组：在控制台把 UDP `20000-50000` 也放行，只放行 443 的话，端口段的包到不了机器，跳跃同样不生效。

## 客户端：端口段地址 + 跳跃间隔

客户端配置对应改两处——服务器地址写成端口段，transport 里加跳跃间隔：

```yaml
server: 你的域名:20000-50000
auth: 你的密码

tls:
  sni: 你的域名

transport:
  type: udp
  udp:
    hopInterval: 30s
```

两个关键参数解释一句：

- `server` 的端口段写法：这叫 "port hopping address"，是客户端识别跳跃模式的开关——写成端口段，客户端才知道要跳；写单个端口，就是普通单端口连接；
- `hopInterval`：客户端换端口的间隔，默认就是 30s，不写也行。也可以设成随机区间（`minHopInterval: 15s` / `maxHopInterval: 45s`），两者不能同时用。

> hopInterval 为什么是客户端行为、服务端不用配？因为"什么时候换端口"是客户端单方面决定的，服务端只管收——段内任意端口的包它都认。所以服务端和客户端的间隔不需要"对齐"，各管各的。

订阅链接（URI）形式同理，端口位置写成端口段即可：

```
hysteria2://你的密码@你的域名:20000-50000/?sni=你的域名&insecure=0
```

间隔用客户端默认的 30s；用的客户端如果支持单独设置跳跃间隔，再按需调整。注意客户端版本别太旧——太旧的版本不认端口段写法，解析会直接报错，先升级客户端。

面板运营侧：如果你用 Xboard 下发 Hysteria2 节点，在面板后台把该节点的端口填成 `20000-50000` 的端口段形式，下发给支持跳跃的客户端即可。建议先拿一个测试账号验证全链路，再全量下发。

## 验证：三步确认跳跃真的生效

```bash
# 1. 服务端：确认 Hysteria2 在监听，且重定向规则存在
ss -ulnp | grep hysteria
iptables -t nat -L PREROUTING -n -v | grep udp
# 用 nftables 的系统看这一条
nft list ruleset | grep -A2 20000

# 2. 换几个段内端口分别探测（任选其一，能通就行）
for p in 20001 30000 49999; do
  timeout 2 bash -c "echo > /dev/udp/你的服务器IP/$p" && echo "$p OK"
done

# 3. 服务端抓包，看客户端是不是真的在换端口连
tcpdump -i eth0 udp portrange 20000-50000 -c 30 | awk '{print $5}' | sort | uniq -c | sort -rn | head
```

第 3 步最有说服力：跑一会儿，如果看到目标端口分散在好几个不同的值上，说明客户端正在按 `hopInterval` 跳跃；如果永远只有一个端口，先回头检查客户端配置里的 `server` 是不是写成了端口段。

然后正常连一次客户端，能上网、速度正常，整条链路就算 OK 了。

## 常见坑

1. **本机防火墙和云安全组只放行了 443**：跳跃的本质是"段内所有端口都要能进"，两处都要放行 UDP 端口段，漏一处就只有第一个端口能通。
2. **手动 iptables 规则没做持久化**：机器一重启规则就没了，表现为"昨天还好好的今天全挂"。排查先 `iptables -t nat -L -n` 看规则还在不在。
3. **权限不够导致官方端口段监听静默失效**：非 root 启动时 Hysteria2 不会报错，只监听段内第一个端口。`ss -ulnp` 看它到底在听几个端口，一眼就能确认。
4. **端口段和其它 UDP 服务冲突**：比如段里包含了你正在用的 WireGuard 或游戏端口。选段之前先 `ss -ulnp` 扫一遍已占用端口。
5. **hopInterval 设得太极端**：设成 5s 会频繁重建 QUIC 路径，开销大、手机端还费电；设成 10 分钟则跳跃基本失去意义。30s–60s 是经过验证的常用值，没特殊理由别动。
6. **和 mimic 冲突**：官方文档明确写了，mimic（TCP 伪装）不能和端口跳跃同时开——开了 mimic 就别配跳跃，二选一。
7. **老客户端不认端口段写法**：直接解析失败、连不上。先升级客户端；如果用户群体客户端版本杂，可以在面板里保留一个单端口节点做兼容。

端口跳跃配完，单端口限速这招基本就废了。但它不是银弹——真遇到整段 UDP 被掐或 IP 被封，还是要靠换 IP、换协议那套组合拳，思路见本仓库的节点被封排查篇。

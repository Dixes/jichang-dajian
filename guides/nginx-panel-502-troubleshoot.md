# Nginx 反代面板出现 502 Bad Gateway：上游端口与超时排查

面板明明昨天还能打开，今天浏览器却只剩一句 502 Bad Gateway，先别急着重装面板，也别急着换服务器。502 的意思很直白：Nginx 收到了你的请求，但它去找后面的面板服务时没拿到有效响应。问题大概率出在「Nginx 与面板之间」这一段，而不是域名解析或面板数据本身。按下面这个顺序查，大多数 502 都能在半小时内定位。

## 先分清：你是哪一种 502

同样是 502，成因完全不同，先看现象再动手，能少走很多弯路：

- **一直 502，从没好过**：多半是反代配置写错了，比如上游端口、监听地址或 `proxy_pass` 指向不对，Nginx 从一开始就没连上面板。
- **之前好好的，重启或升级后突然 502**：多半是面板服务没起来、监听端口变了，或者升级后依赖没装好，服务一起就退出。
- **偶尔 502，刷新又好了**：多半是面板响应太慢、超时了，或者服务器资源一时吃紧，Nginx 等不到响应就断了。

分清属于哪一类，后面的排查就只盯对应的环节，不用全量重做一遍。

## 第一步：确认面板服务本身在不在跑

反代只是「传话的人」，先确认「说话的人」还活着。登录面板机，查服务状态和监听端口：

```bash
# 查看面板服务状态（服务名以你部署时的实际名称为准）
systemctl status xboard

# 查看本机有哪些端口在监听，确认面板端口是否在列
ss -tlnp | grep -E '8080|8000|9000'

# 绕过 Nginx，直接在本机访问面板，看它自己能不能响应
curl -I http://127.0.0.1:8080
```

上面命令里的端口只是示例，一定要换成你部署时给面板配置的实际端口。如果 `systemctl status` 显示服务是失败状态，先看它的日志，不要直接重启了事：

```bash
# 看面板服务最近的日志，找报错的第一行
journalctl -u xboard -n 100 --no-pager
```

日志里常见的几种情况：数据库连不上、配置文件语法错了、依赖缺失、端口被别的进程占了。数据库和配置问题要先修根因，只重启服务的话，起来还是会再挂。如果是端口冲突，先把占用端口的旧进程处理掉，或者把面板改到空闲端口，并同步改掉 Nginx 里的上游指向——两边改一边就会继续 502。

## 第二步：核对 Nginx 的上游配置

面板本机能访问，但经过 Nginx 就 502，问题就在反代配置。打开对应站点的 Nginx 配置，重点核对三处：

```nginx
server {
    listen 80;
    listen 443 ssl;
    server_name panel.example.com;

    location / {
        # 必须指向面板实际监听的地址和端口，不要照抄别人的示例端口
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

这几个参数各有原因：`proxy_pass` 写错，Nginx 就会去连一个不存在的服务；`Host` 不传真实域名，面板按域名做的校验和跳转就可能出错；`X-Real-IP` 和 `X-Forwarded-For` 是让面板拿到访客真实 IP，没有它们，面板日志里全是 127.0.0.1，以后做 IP 限制和排障都会失真。

改完配置不要直接 reload，先测语法，再看 Nginx 自己的错误日志：

```bash
# 检查 Nginx 配置语法，通过后再重载
nginx -t && systemctl reload nginx

# 看 Nginx 报错日志，502 发生时这里通常有对应的上游记录
tail -n 100 /var/log/nginx/error.log
```

错误日志里如果出现 `connect() failed (111: Connection refused)`，就是上游端口没人监听，回到第一步；如果出现 `upstream timed out`，则是响应超时，往第三步走。如果你用的是 Caddy 而不是 Nginx，可以对照本仓库的另一篇教程思路来核对反代写法：[Caddy 反代面板的完整配置示例](guides/caddy-reverse-proxy-panel.md)。

## 第三步：处理超时与响应慢导致的 502

面板生成订阅、拉取节点统计时偶尔会比较慢，Nginx 默认的等待时间一到就断开，浏览器看到的就是间歇性 502。这种情况要把超时参数放宽，而不是一味加机器：

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_connect_timeout 10s;
    proxy_send_timeout 60s;
    proxy_read_timeout 120s;
}
```

三个参数分工不同：`proxy_connect_timeout` 是 Nginx 连上游最多等多久，面板就在本机，一般 10 秒足够；`proxy_send_timeout` 是发请求给上游的等待时间；`proxy_read_timeout` 是等上游回响应的时间，订阅生成这类慢接口主要靠它兜底。把 `proxy_read_timeout` 设到 120 秒后，再观察一段时间——如果间歇性 502 消失，说明就是慢响应问题；如果还是频繁出现，就要回头看面板机是不是内存或 CPU 长期吃满，那是资源问题，不是光调超时能解决的。

## 验证：确认 502 真的修好了

不要只刷一次浏览器就宣布修好，按下面三步验证：

```bash
# 1. 本机直连面板，应当返回 200 或 302
curl -I http://127.0.0.1:8080

# 2. 经过 Nginx 访问域名，也应当返回 200 或 302
curl -I https://panel.example.com

# 3. 再看一次 Nginx 错误日志，确认没有新的 502 记录
tail -n 50 /var/log/nginx/error.log
```

三步都通过后，再用浏览器无痕模式打开一次面板，登录、打开一次订阅页面、打开一次节点列表——这几个页面都正常，才算真正通过。只验证首页是不够的，慢接口的问题往往藏在订阅生成页。

## 常见坑

- **改了面板端口，忘了改 Nginx**：这是最常见的 502 来源。面板端口一变，Nginx 配置、防火墙放行端口、面板自身的监听配置要一起改，只改一处必出问题。
- **改完配置忘了 reload**：`nginx -t` 通过不等于生效，必须 `systemctl reload nginx`，否则你排的是旧配置的错。
- **把 502 和 504 混为一谈**：502 是上游没给有效响应，504 是上游响应超时。先看错误日志里的关键字再动手，方向错了会越修越乱。
- **面板和 Nginx 不在同一台机器**：这时 `127.0.0.1` 就不能用了，`proxy_pass` 要写面板机的内网 IP，同时面板机防火墙要放行 Nginx 所在机器的访问，只放行 Nginx 的 IP，不要对全网放开面板端口。
- **证书刚换完就 502**：先别怀疑证书，证书问题通常表现为浏览器证书报错而不是 502。先按上面三步查上游，确认上游没问题再回头看证书配置。

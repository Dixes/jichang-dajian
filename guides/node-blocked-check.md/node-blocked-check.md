# 落地机是不是被墙了：常用检测方法

节点突然连不上了，第一反应往往是“IP 被墙了”。但先别急着下这个结论：服务自己挂了、端口没放行、配置改错了、证书过期了，表现都和“被墙”很像。直接换 IP 换域名一通操作，不仅费钱，还可能把一个本来五分钟能修好的配置问题，变成一场毫无头绪的迁移。本文给的是一套从内到外、从本机到境外的排查顺序，帮你先把“被墙”这个结论坐实，或者排除掉。

本文默认的场景是：你运营一台落地机（节点端已装好并对接面板），用户反馈连不上，或者你自己从国内测试连不上。面板、节点端的部署不在本文范围内。

## 先分清：是被墙，还是服务本身挂了

被墙的典型特征是“从某些网络看是死的、从另一些网络看是活的”，而服务挂了是“从哪里看都是死的”。所以第一步永远是在服务器本机上确认服务本身没问题，这一步不做，后面所有的境外测试都没有意义。

```bash
# 1. 节点端服务是不是在跑
systemctl status v2bx
# 输出 active 才算通过；failed 或 inactive 先看日志修服务，不要往被墙上想

# 2. 端口是不是真的在监听
ss -tlnp | grep 你的节点端口
# 能看到监听记录，说明核心已经把端口占住了；看不到，先查配置和核心日志

# 3. 本机能不能自己连通端口
curl -v --connect-timeout 5 telnet://127.0.0.1:你的节点端口
# 本机都连不上，问题在服务或配置，不在网络
```

> 为什么要先查本机？因为面板显示节点在线，只说明面板到节点的管理通道是通的，不等于面向用户的协议端口是通的。两者走的端口、走的路径可能完全不同，面板在线不能证明用户侧端口正常。

如果本机三项都通过，但面板显示节点离线，那要先把“面板连不上节点”和“用户连不上节点”这两类问题分开：前者按本仓库的 [V2bX 对接失败：面板显示节点离线怎么办](v2bx-offline-troubleshoot.md) 排查，不要混成一锅。

## 第一步：换视角测试，别只用一个网络下结论

只用一个网络测一次就下结论，是误判的最大来源。你手头的测试网络可能本身就有问题：公司网络、校园网、某个宽带运营商的出口，都可能单独出故障。至少要拿到两个不同视角的结果再对比：

- **视角一：服务器本机**，上面已经做过，确认服务和监听正常。
- **视角二：另一台境外服务器**，通过 SSH 登录后，从那里向落地机发起连接。
- **视角三：国内测试环境**，也就是用户实际使用的网络环境（注意是测试连通性，不是拿用户账号去反复试）。

从境外服务器测试时，重点看 TCP 层通不通，而不是看协议能不能握手成功：

```bash
# 在另一台境外服务器上执行，把 203.0.113.10 换成你的落地机 IP
# 203.0.113.10 是文档示例地址，实际测试时换成你自己的 IP
nc -vz -w 5 203.0.113.10 你的节点端口
# 输出 succeeded / connected，说明 TCP 是通的

# 再看路由走到哪里断了（需要装 mtr，没有就用 traceroute 代替）
mtr --report-wide --report-cycles 20 203.0.113.10
# 重点看最后一跳：是全程都有响应、还是在某个中间节点之后全部丢包
```

> 为什么要分开看 TCP 层和协议层？因为防火墙拦截、IP 封锁、协议特征识别，断的层次不一样。TCP 都连不上，和 TCP 通了但协议握手被掐掉，是两种完全不同的故障，处理办法也不一样。只测“能不能连上”这一个结果，你分不清断在哪一层。

再提醒一个常见误区：**ping 不通不等于被墙**。很多服务器默认禁 ICMP，或者云厂商安全组根本没放行 ICMP，ping 全程丢包但 TCP 端口好好的，这种情况非常普遍。ping 只能当辅助参考，不能当判决证据。反过来也一样：ping 通了也不代表协议端口通，ICMP 和 TCP 走的是不同的规则。

## 第二步：换端口、换域名交叉验证，定位是封 IP 还是封端口

如果境外能通、国内不通，接下来要判断封的是整个 IP，还是某个端口，或者是域名解析出了问题。这三者要分开测，一次只换一个变量：

```bash
# 测法一：换一个不常用的高位端口做对照
# 在节点端临时加一个监听端口（按你的核心配置来，示例只是思路）
# 然后从国内测试新端口：
nc -vz -w 5 203.0.113.10 新端口
# 原端口不通、新端口通 → 很可能是原端口被针对；两个都不通 → 更像 IP 层面的问题

# 测法二：对比 IP 直连和域名解析
dig +short node.example.com
# node.example.com 是示例域名，换成你自己的节点域名
dig +short @8.8.8.8 node.example.com
# 两次结果不一致，或者国内解析返回了明显不对的地址，要先怀疑 DNS 层面的问题
# 而不是直接认定 IP 被封
```

> 为什么要一次只换一个变量？因为同时换 IP、换端口、换域名之后“通了”，你根本不知道是哪一个改动起的作用，下次再出问题还是没经验。而且无意义的频繁更换，会让面板配置、用户订阅、域名解析全都跟着乱，排查成本越滚越大。

域名解析这里还要多说一句：如果你用的是域名接入，国内用户解析异常时，先看是不是域名本身的问题——域名过期、解析商故障、DNS 缓存没刷新，都会表现为“突然连不上”。用不同解析器（运营商 DNS、公共 DNS）各查一次，再查域名到期时间和解析记录，确认无误后再往 IP 封锁的方向想。

## 第三步：看日志和连接特征，给“被墙”定性

前面几步只能告诉你“哪里不通”，日志能告诉你“怎么个不通法”。不同特征指向不同原因，对照下面这张表看，比凭感觉猜要准：

| 现象 | 更可能的指向 |
| --- | --- |
| 境外 TCP 通、国内 TCP 超时（无任何响应） | IP 或端口在国内方向上被丢弃 |
| TCP 能建立，但协议握手很快被重置（RST） | 传输层或协议层被干预 |
| TCP 通、握手超时、日志里完全没有连接记录 | 流量在到达服务器之前就被丢弃 |
| 日志里有连接记录，但握手失败、证书报错 | 配置、证书或协议参数问题，不是网络封锁 |
| 只有某个运营商、某个地区不通，其他地区正常 | 区域性网络问题，不一定是整 IP 被封 |
| 全天都通、只在晚高峰断断续续 | 更像拥塞或线路质量问题，先查带宽和负载 |

查日志时，重点看时间点能不能和用户反馈对上：

```bash
# 看节点端核心和 V2bX 的近期日志，找用户反馈时间点附近的记录
journalctl -u v2bx --since "1 hour ago" | tail -n 100
# 找这三类信号：有没有连接进来、握手走到哪一步失败、有没有大量异常连接
# 如果日志里在故障时间点完全没有新连接，说明流量根本没到服务器
```

> 为什么日志比感觉可靠？因为“用户说连不上”这句话本身包含很多种可能：他自己的网络问题、他用的网络环境问题、订阅没更新、节点配置问题，都有可能。日志里有没有连接记录，是区分“流量没到”和“到了但处理失败”的硬证据，没有这条证据就不要轻易换 IP。

另外注意时间窗口：只在某个时段不通、其他时段正常，或者只有个别用户反馈、多数用户正常，都不适合直接按“被墙”处理。先收集多几个用户反馈的时间、地区、运营商，看有没有共同点，单个用户的孤例很可能只是他自己的网络问题。

## 第四步：确认之后的处置顺序，别一上来就全换

如果上面几步都走完了，结论确实是 IP 或端口层面被封，处置也有个先后顺序，从成本最低的开始：

1. **先换端口**：如果只是单个端口被针对，换一个高位端口、更新面板配置、让订阅重新下发，是最快的恢复办法。
2. **再换域名解析**：如果问题在 DNS 层，换解析商或换域名，比换 IP 便宜得多。
3. **最后换 IP**：只有确认整个 IP 都不通、且换端口无效时，才考虑向云厂商申请换 IP，或者把节点迁移到新机器。换 IP 之后，面板里的节点地址、域名解析、订阅链接都要同步改，漏一项就会出现“换了 IP 还是有人连不上”的二次故障。
4. **换完要复测**：按第一步的方法，从境外服务器和国内测试环境各测一次，确认新地址在两个视角下都通，再通知用户更新订阅。不要只在服务器本机测完就宣布恢复。

还有一个容易忽略的点：**换 IP 之前，先确认不是你自己的操作触发的**。比如短时间内大量异常连接、端口扫描、配置错误导致核心反复重启，这些都可能让云厂商或机房侧采取临时限制。先看日志里有没有异常流量，把自己的问题先排除，再去换资源，否则新 IP 也可能很快重蹈覆辙。

## 验证清单：确认被墙之前，这几项都要打勾

- [ ] 服务器本机服务 active、端口在监听、本机能连通端口
- [ ] 至少两个不同视角测试过（境外服务器 + 国内测试环境），结果能对比
- [ ] ping 的结果只当参考，没有用 ping 不通直接下结论
- [ ] 换端口对照测过，能区分是封端口还是封 IP
- [ ] 域名解析用不同解析器查过，排除了域名和 DNS 层面的问题
- [ ] 日志里故障时间点的连接记录看过，能说清流量是“没到”还是“到了但失败”
- [ ] 多个用户反馈的时间、地区、运营商对过，不是单个用户的孤例

这七项都打勾、且指向一致，结论才站得住脚；缺任何一项，都先补上那一项再下结论。

## 常见坑汇总

- **ping 不通就断定被墙**：很多服务器禁 ICMP，ping 丢包很常见，TCP 端口通才是硬指标。
- **只用一个网络测一次就下结论**：单个网络本身出故障的概率不低，至少两个视角对比。
- **面板在线就等于用户侧正常**：管理通道和用户协议端口是两回事，面板在线不能证明用户端口通。
- **同时换 IP、换端口、换域名**：一次换一个变量，否则不知道哪个改动起了作用。
- **日志都不看就换资源**：日志里有没有连接记录，是区分“流量没到”和“处理失败”的关键证据。
- **把个别用户反馈当成全局故障**：先对时间、地区、运营商，孤例很可能只是用户自己的网络问题。
- **把晚高峰抖动当成被墙**：时段性问题先查带宽、负载和线路质量，不要直接换 IP。
- **域名问题当成 IP 问题**：域名过期、解析故障、缓存没刷新，都会表现为突然连不上，先查解析。
- **换了 IP 忘了同步配置**：面板节点地址、域名解析、订阅链接漏改一项，就会出现二次故障。
- **换完只在本机验证**：恢复确认也要境外和国内两个视角都测过，再通知用户。

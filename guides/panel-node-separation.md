# 面板机与落地机分离部署注意事项

新手搭机场容易把面板和节点端塞进同一台 VPS：面板一装就是 MySQL、PHP、Redis、队列进程一整套，再加上 Xray 或 V2bX，资源一争就全都不稳；一台机器既对用户开放面板又承担节点流量，一端出问题也会牵连另一端。分离部署就是把这两件事拆到两台机器上：面板机只负责面板、用户、订单和订阅下发，落地机只负责跑节点协议、转发流量。下面按实操顺序讲怎么做、哪些地方最容易配错。

## 分离之后的结构长什么样

分离部署最少需要两台 VPS，角色分工如下：

- **面板机**：装 Xboard 这类面板，对外提供面板网站和订阅地址。它不直接跑节点协议，不承载用户流量，只在需要时通过 API 把节点配置推给节点端。
- **落地机**：装 V2bX 这类节点端，只和面板机通信、只跑节点协议。它不装面板、不存用户数据，面板挂了它手头已有的配置还能继续跑一阵子，新订阅下发会暂时停住。
- **通信方向**：正常情况下是节点端主动向面板拉取配置，或者面板通过节点端提供的 API 接口下发配置，具体方向取决于你用的面板和节点端版本。无论哪种，通信都只发生在面板机与落地机之间，不需要把节点端的 API 暴露给全网。

这样分的好处很实在：面板机可以选便宜稳定的机器，落地机按线路和带宽去选；面板升级重启不影响已在线的节点，落地机换 IP、换线路也不用动面板数据。面板全家桶和节点端挤一台是内存不够用的典型成因，分离是更彻底的解法，细节见本仓库的 [1G 小内存 VPS 跑面板的优化清单](low-memory-vps-panel.md)。

## 第一步：先定好两台机器的分工与地址

动手前先定一张小表，之后所有配置都按它填：

```text
面板机：IP 203.0.113.10，域名 panel.example.com，只跑面板
落地机：IP 198.51.100.20，域名 node.example.com，只跑节点端
面板 API 地址：https://panel.example.com/api/v1/client/subscribe?token=你的订阅密钥
节点端 API 端口：示例 6688（只允许面板机 IP 访问，见下文防火墙一节）
```

注意两点：面板域名和节点域名分开，不要共用一个域名区分端口，之后换机器、换证书都更干净；两台机器的 IP 都记下来，防火墙和面板后台填节点地址时都要用到。

## 第二步：面板机只装面板，不装节点端

面板机上按面板自己的流程装好 Xboard，确认能打开、能登录后台、能创建套餐和用户即可。不要顺手把 V2bX、Xray 也装上，不用反而多出常驻进程和暴露面。

面板机上要单独确认三件事：

```bash
# 1. 面板服务正常，HTTP 状态是 200 而不是 502
curl -s -o /dev/null -w "%{http_code}\n" https://panel.example.com

# 2. 定时任务在跑：订阅生成、流量统计、过期清理都依赖它
#    Xboard 的队列与计划任务按官方文档配好后，检查进程在不在
ps aux | grep -E "queue|schedule" | grep -v grep

# 3. 系统时间是对的：面板签发订阅、判断过期都看时间，差几分钟就会出怪问题
timedatectl
```

> 为什么时间要单独检查？两边时间差大了，订阅有效期、流量统计周期都会对不上。两台机器都要开 NTP 同步，这是分离部署最容易忽略的一类故障源。

## 第三步：落地机只装节点端，指向面板

落地机上装 V2bX，填面板地址和节点标识。不同版本配置文件位置和字段名略有差别，核心就三项：面板地址、节点 ID、通信密钥：

```yaml
# V2bX 配置核心项（字段名按你所用版本调整）
# 面板地址：填面板机的订阅/API 地址
ApiHost: "https://panel.example.com"
# 节点 ID：必须和面板后台创建的节点 ID 一致，差一位就是另一台节点
NodeID: 1
# 通信密钥：和面板后台该节点配置的密钥一致，密钥错了面板会拒绝下发
ApiKey: "请填面板后台生成的密钥，不要用示例值"
```

填完启动 V2bX，看日志确认它成功从面板拉到了配置：

```bash
# 看 V2bX 最近的日志，找“拉取配置成功”“节点已上线”一类的信息
journalctl -u v2bx -n 50 --no-pager

# 确认节点端进程在监听协议端口（端口号按面板里该节点的配置来）
ss -tlnp | grep -E "443|8443"
```

> 为什么节点 ID 和密钥要逐字核对？分离部署配错了不会立刻报错，表现常常是面板后台节点一直离线，或节点跑起来了但用的是旧配置。先核对能省掉后面一大圈排查。

## 第四步：节点端 API 只放行面板机 IP

这是分离部署最关键的安全配置。节点端为了让面板管理它，往往会开一个 API 端口，对全网开放等于把管理入口摆在公网上。正确做法是只允许面板机 IP 访问，其他来源一律拒绝。

```bash
# 以 UFW 为例：先默认拒绝入方向，再只放行面板机 IP 访问节点端 API 端口
# 注意：执行前确认你当前的 SSH 会话不会被默认拒绝规则断掉，先放行 SSH
ufw allow 22/tcp
ufw allow 443/tcp
# 节点端 API 端口示例 6688：只允许面板机 203.0.113.10 访问
ufw allow from 203.0.113.10 to any port 6688 proto tcp
ufw enable
ufw status numbered
```

如果用云厂商安全组而不是机内防火墙，同样逻辑：给节点端 API 端口加一条来源为面板机 IP 的规则，不要写成 `0.0.0.0/0`。面板机换机器、IP 变了要同步改规则，否则面板推不动配置，节点会离线。

> 为什么面板机也要放行 443？面板机对外提供面板网站和订阅地址，用户和节点端都要能访问它；节点端 API 的调用方只有面板机一个，多放一个来源就多一份被扫描的风险。

## 第五步：证书与域名分开处理

面板机和落地机的证书不要混着配：

- **面板机**：给 `panel.example.com` 申请证书，走面板站点的 Nginx 或 Caddy 配置，自动续期配好。
- **落地机**：节点协议如果用 Reality，一般不需要传统证书，靠 Reality 密钥；如果用 WS + TLS + CDN 这类方案，证书配在节点域名或 CDN 侧，按对应方案的文档来，不要把面板机的证书文件直接拷到落地机上复用。

```bash
# 面板机上确认证书有效期（示例域名按实际改）
echo | openssl s_client -connect panel.example.com:443 -servername panel.example.com 2>/dev/null \
  | openssl x509 -noout -dates

# 落地机上确认协议端口能通（从面板机测一次，顺带验证防火墙没把正常流量拦掉）
curl -v https://node.example.com:443 --max-time 10
```

证书混用的坑在于：面板机证书续期后，落地机上那份旧证书不会跟着更新，过期节点就断。域名和证书一一对应，各自续期，出问题定位也快。

## 第六步：验证分离部署真的通了

两边都装好、防火墙也配好后，按下面顺序验证，不要只看面板后台一个绿灯就收工：

```bash
# 1. 面板机能访问节点端 API（从面板机上测，返回正常即防火墙规则生效）
curl -s https://198.51.100.20:6688/ --max-time 10

# 2. 落地机能访问面板 API（从落地机上测，确认出方向没被拦）
curl -s "https://panel.example.com/api/v1/client/subscribe?token=你的订阅密钥" --max-time 10 | head -c 200

# 3. 面板后台节点状态：新建一个测试用户、生成订阅，看节点是否显示在线
# 4. 流量统计：用测试订阅产生一点流量，面板后台该节点的流量统计应当在几分钟内变化
```

任何一项不通过，先回到对应步骤查：后台离线查节点 ID、密钥和防火墙；订阅拉不到查面板机时间和证书；流量统计不动查节点端日志有没有成功上报。定位口诀是：**先分清是面板侧、落地侧还是中间网络的问题，再进对应机器查日志**。

## 常见坑

1. **角色装反**：面板机上装了节点端、落地机上装了面板，或两台都装全套。角色一乱，防火墙和证书全跟着乱，先按开头分工表定死角色。
2. **节点端 API 对全网开放**：没加来源限制，或安全组写了 `0.0.0.0/0`。这是最不该省的一步，务必只放行面板机 IP。
3. **节点 ID 或密钥抄错一位**：后台离线、日志报认证失败，十有八九是这里错了。从面板后台复制，不要手打。
4. **两台机器时间不同步**：订阅过期判断、流量周期对不上，先查 `timedatectl`，两边都开 NTP。
5. **面板机换 IP 后忘了改防火墙**：落地机放行规则还是旧 IP，节点会突然离线。换 IP 时把防火墙规则列进迁移清单。
6. **证书混用、续期不同步**：面板证书拷到落地机复用，续期后落地机那份过期。域名和证书一一对应，各自续期。
7. **只验面板后台绿灯**：后台在线不等于订阅能用、流量能统计，一定要走到测试订阅、产生流量这一步再收工。

分离部署多一台机器、多几条防火墙规则，换来的是面板和节点互不拖累：面板升级重启不影响在线节点，落地机换线路不用动面板数据。把分工表、防火墙规则、节点 ID 与密钥写下来存好，之后扩第二、第三台落地机时照同一套流程复制就行。

# V2bX 流量统计不准的排查顺序

流量对不上的抱怨，在机场运营里几乎每周都会出现一次：用户说“我明明没用多少，面板却显示跑了几十 GB”；或者反过来，用户刷视频刷了一晚上，面板流量纹丝不动。两种情况看起来相反，根源往往在同一条链路上——节点端采集、上报、面板端汇总，这三环里只要有一环口径不一致，数字就对不上。

先说一个判断原则：流量统计问题很少是“某一个开关坏了”，多半是“两边算的不是同一笔账”。所以排查不要一上来就重启节点、重装面板，而是按“先定口径、再查上报、最后查面板”的顺序，一环一环缩小范围。下面这套顺序，就是按这个思路排的。

## 第一步：先定口径——你说的“不准”，到底是哪两个数在比

动手之前，先把“不准”翻译成可验证的说法。最常见的几种，排查方向完全不同：

- **面板显示 > 用户实际用量**：怀疑重复上报、多节点重复统计、或把节点间中转流量也算进了用户账单；
- **面板显示 < 用户实际用量**：怀疑上报丢数据、节点端统计没开、或核心版本不支持流量统计；
- **面板显示为 0、但用户能正常上网**：怀疑统计功能根本没接通，或节点与面板的通信只通了控制面、没通统计面；
- **流量时有时无、隔天突然跳变**：怀疑上报间隔与面板定时汇总任务错位，或者节点重启后计数器归零、面板却按增量累加。

把你的情况对号入座，再去看下面对应的环节。很多人上来就改配置，改了半天才发现自己和用户比的根本不是同一时间段的数——面板按自然日汇总、用户按自己上次充值那天起算，口径一开始就没对齐。

```bash
# 先在面板后台确认三个口径，避免一开始就比错了数
# 1. 统计周期：是自然日、自然月，还是按用户购买周期？
# 2. 流量单位：面板显示的是 GB 还是 GiB？（1 GB = 1000 MB，1 GiB = 1024 MiB，差 7% 左右）
# 3. 统计对象：是“用户总流量”，还是“某个节点上的流量”？
#    用户同时连多个节点时，单节点数和总账本来就不一样
```

> 为什么口径要先于技术排查？因为 7% 的单位差、跨时区的自然日边界、多节点分摊，这些“对不上”在技术上全是正常的，改配置改不掉。你先确认比的是同一笔账，后面查到的每一个异常才有意义。

## 第二步：查节点端——核心有没有在统计，统计的是谁

V2bX 本身不直接产生流量数据，它是把节点核心（Xray、sing-box 等）的流量计数读出来、再上报给面板。所以节点端要确认三件事：核心在跑、统计开了、统计对象是对的。

```bash
# 1. 确认 V2bX 进程在跑、核心也在跑
ps aux | grep -E 'v2bx|V2bX' | grep -v grep
# 如果 V2bX 在、核心不在，用户流量根本不会经过核心统计

# 2. 看 V2bX 的日志，找统计相关的报错或警告
#    日志路径按你的部署替换
tail -100 /etc/V2bX/v2bx.log
#    重点找这几类：上报失败、核心连接失败、配置解析失败
#    任何一类出现，面板数字停滞或跳变都有了解释

# 3. 确认核心配置里流量统计是开启的
#    Xray 核心：检查 config 里 stats / policy.levels.statsUserUplink、statsUserDownlink 是否为 true
#    sing-box 核心：检查实验性统计或 V2bX 对接配置里是否启用了流量上报
#    统计没开，核心跑得再稳，面板也只能拿到 0
```

> 为什么核心统计开关这么关键？V2bX 是“搬运工”不是“生产者”：核心不统计，V2bX 拿到的就是空数；核心统计了但按“入站”而不是“用户”维度统计，V2bX 搬过去的数和用户账单也对不上。先确认生产者，再查搬运工。

还有一个容易被忽略的点：**核心版本**。不同版本的核心，流量统计字段和行为可能有变化——有的版本重启后计数器归零，有的版本对某些协议（例如 Hysteria2、TUIC）的统计口径不一样。如果你最近刚升级过核心、流量就是从那时起不准的，先把版本变化列为第一嫌疑人，对照核心的更新说明确认统计行为有没有变。

## 第三步：查上报链路——数有没有按时、完整地送到面板

节点端统计正常，接下来看数有没有送到面板。V2bX 上报给面板一般是定时任务：每隔一段时间（例如 60 秒）把这段时间内的增量发过去。这里最容易出三种问题：

```bash
# 1. 上报间隔是不是设得太长
#    在 V2bX 配置里找到上报间隔（NodeInterval / 更新间隔类配置项）
#    间隔太长（例如 10 分钟）时，面板数字会长时间不动、然后突然跳一大截
#    看起来像“不准”，其实只是刷新慢

# 2. 节点与面板之间的时间是否同步
#    节点和面板的系统时间差几分钟，就会让“这小时的流量”被记到“上一小时”
#    跨自然日边界时尤其明显：用户以为昨天用了，面板记到了今天
timedatectl status
#    看到 NTP synchronized: yes 才是正常；如果时间不同步，先修时间再谈统计
#    修时间：timedatectl set-ntp true，然后等几分钟让时间同步完成

# 3. 检查上报有没有丢包或被防火墙挡掉
#    看 V2bX 日志里的上报失败记录，连续失败说明链路有问题
#    回到节点端 API 防护的思路反向检查：是不是防火墙规则把上报端口或面板地址挡住了
#    （注意：这里是节点主动上报给面板，和面板主动拉取是两条方向，别查反了）
```

> 为什么时间同步要单独列出来？因为流量上报本质上是“时间戳 + 增量”：时间戳错了，增量就会被记到错误的统计周期里。面板按日汇总时，错位一天的流量在用户看来就是“昨天明明用了、今天却多了”。先对表，再对账。

上报间隔还有一个连锁影响：**节点重启**。很多核心重启后流量计数器归零，V2bX 上报的是“当前计数器的值”还是“与上次上报的差值”，不同实现处理不一样。如果实现是按差值累加，重启后计数器从一个大数变回 0，面板可能把这次差值算成负数、直接丢弃——于是重启那段时间的流量就“丢了”。节点频繁重启（例如内存不足被 OOM 干掉、定时任务重启），流量就会隔三差五少一段。节点重启频繁的话，先按本仓库的低内存优化思路把重启原因解决了，统计自然就稳了。

## 第四步：查面板端——汇总、重置与多节点去重

节点端和上报链路都没问题，问题就落在面板端。面板端的排查按下面这个顺序：

1. **定时汇总任务在不在跑**：面板通常有个定时任务，把各节点上报的原始数据汇总成用户账单。这个任务挂了，原始数据在、账单不更新，表现就是“流量不动”。去面板后台的任务/队列状态里确认汇总任务最近一次成功执行的时间。
2. **流量重置规则对不对**：用户续费、套餐变更、手动重置后，流量计数应该归零或按新套餐起算。重置规则配错了（例如按自然月重置、但套餐是按购买日周期），用户账单就会在月中突然清零或翻倍。
3. **多节点有没有重复计算**：同一个用户同时连两个节点，两个节点都上报了他的流量，面板汇总时如果没有按用户去重、或者把中转节点的流量也算了一次，用户账单就会翻倍。重点检查中转架构：中转节点（转发流量）和落地节点（出站流量）如果都被计入同一用户的账单，同一字节就被算了两次。
4. **数据库里原始数据对不对**：面板后台显示的数是汇总结果，想定位到底是哪一环错了，要去数据库里看原始上报记录。找一个对不上的用户，对比“各节点上报的原始增量之和”和“面板显示的账单数”，两者相等说明上报没问题、问题在汇总；两者不等说明上报或入库环节丢了数。

```bash
# 面板端定位的通用思路（以 MySQL 为例，表名按你所用面板的实际结构替换）
# 1. 先查某个用户的原始上报记录之和
#    SELECT SUM(upload + download) FROM 流量记录表 WHERE user_id = 目标用户;
# 2. 再查面板显示给该用户的账单数
#    对比两个数：相等 → 汇总逻辑问题；不等 → 上报或入库问题
# 3. 如果原始记录本身就缺了某几天，先回第三步查那几天的上报日志
```

> 为什么面板端要最后查？因为面板是“算账的人”：上报的数错了，它算出来的账单必然错；上报的数对了、它算错了，才是它自己的问题。先证明上报的数是对的，再去怀疑算账的人，否则你在面板配置里改来改去，改的都是无辜的配置。

## 验证：改完之后，用一笔可控流量做对照实验

不管改了哪一环，改完都要做一次对照实验，而不是等用户反馈。找一个测试账号，只连一个节点，跑一笔已知大小的流量，再对比面板：

```bash
# 1. 建一个测试用户，流量清零，确认面板显示为 0
# 2. 测试账号只连一个节点，避免多节点分摊干扰
# 3. 在节点上下载一个已知大小的文件（例如 100MB 的测试文件）
#    注意：用直连下载、不要走中转，避免中转节点重复计入
curl -o /dev/null http://speedtest.example.com/100MB.bin
#    （换成你自己的测试文件地址，大小要事先确认）
# 4. 等一个上报间隔（例如 60 秒）后再加汇总任务的执行间隔
#    然后去面板看测试账号的流量：应该在 100MB 上下浮动（有协议开销，略高于 100MB 是正常的）
# 5. 如果差值在 5% 以内，统计链路就是通的；如果差得多甚至为 0，回到前面四步继续查
```

> 为什么对照实验要用“单节点 + 已知大小”？因为多节点分摊、中转重复、单位换算这三个干扰项会把实验结果搅浑。单节点、已知大小、等够上报间隔，三个条件齐了，实验结果才有判断力。

对照实验还有一个用处：它能区分“统计不准”和“统计延迟”。很多用户投诉的“流量不动”，其实只是上报间隔 + 汇总间隔叠加后的延迟——跑完流量等两分钟再看，数就上来了。实验里特意等够两个间隔，就是为了把延迟排除掉。

## 常见坑汇总

- **拿面板数和客户端自带统计直接比**：客户端统计的是设备上所有流量（包括直连、其他应用），面板只统计走节点的流量，两者口径不同，差多少都正常。
- **单位混用**：面板按 GB、用户按 GiB 算，7% 的差看起来像“偷流量”，其实只是单位。
- **只看总量、不看时间段**：用户按购买周期算、面板按自然月算，月中对账必然对不上，先对齐周期再谈数字。
- **节点时区没统一**：节点在 UTC、面板在东八区，自然日边界错 8 小时，跨日流量全记偏。
- **核心统计没开就怪 V2bX**：V2bX 只搬运不生产，核心统计开关没开，面板永远是 0。
- **上报间隔设得太长**：10 分钟才报一次，面板长时间不动、然后突然跳变，用户以为统计坏了。
- **中转和落地重复计入**：同一字节在中转节点和落地节点各算一次，用户账单直接翻倍，中转节点一般不应该计入用户账单。
- **节点频繁重启丢增量**：计数器归零后差值变负、被面板丢弃，重启那段时间的流量就没了，先解决重启原因。
- **核心升级后统计口径变了**：升级前先看更新说明，升级后立刻做一次对照实验，别等用户投诉才发现。
- **重置规则和套餐周期错位**：自然月重置配购买日套餐，月中清零或翻倍都是规则错，不是统计错。
- **汇总定时任务挂了没人知道**：原始数据在入库、账单不更新，定期看一眼任务最近成功时间，比等投诉便宜得多。
- **多节点分摊没和用户说清楚**：用户同时连两个节点，单节点数和总账本来就不一样，解释时先说明这是两个数。

定位流量问题时，如果节点根本连不上、面板显示离线，那是另一类问题——先按本仓库的 [V2bX 对接失败：面板显示节点离线怎么办](v2bx-offline-troubleshoot.md) 把连通性修好，统计问题要等节点在线之后才有意义。

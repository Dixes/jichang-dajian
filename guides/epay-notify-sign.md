# 易支付对接常见坑：异步通知验签失败

面板接好易支付之后，最让人头疼的一种故障是这样的：用户明明已经付款成功，易支付后台也显示交易完成，可面板里的订单还停留在“待支付”，用户来问为什么没开通，管理员手动补单补到手软。十有八九，问题出在异步通知这一环——易支付把支付结果推回来了，但面板验签没通过，于是把这条通知当成非法请求直接丢掉了。同步跳转（用户付款后浏览器跳回的页面）只能用来展示结果，不能用来开通，因为用户可能付款后直接关掉页面，根本不会走跳转；真正决定开通的，必须是服务端收到的异步通知。所以验签失败不是小问题，它等于断了“付款—开通”这条链。

## 先搞清楚：异步通知到底怎么验

易支付的异步通知是一次服务端到服务端的 POST 回调：易支付服务器主动请求你面板上配置的通知地址（notify_url），带上订单号、金额、支付状态和签名。面板收到后要做三件事：第一，用双方约定的密钥和签名算法，把收到的参数重新算一遍签名；第二，把算出来的签名和通知里带的签名比对，一致才算通过；第三，确认订单号和金额跟自己数据库里的订单对得上，再把订单置为已支付并开通套餐。

验签失败时，先别急着怀疑易支付那边出问题。按下面的顺序查，大多数情况半小时内能定位：先看面板日志里有没有收到这条通知，再看签名算法和密钥对不对，最后看参数有没有在传输中被改动。三个环节逐个排除，不要同时改好几个地方，否则改对了也不知道是哪一处起的作用。

```bash
# 排查第一步：确认通知到底有没有到达你的服务器
# 1. 看面板或 Web 服务的访问日志，搜易支付回调的路径，例如 /api/payment/notify
# 2. 看易支付商户后台的通知记录：显示“通知成功”还是“通知失败”
# 3. 如果日志里完全没有这条请求，问题不在验签，而在通知地址或网络层面
# 4. 如果日志里有请求、返回的却是 4xx 或 5xx，再往下查签名环节
```

> 为什么先查“收到没有”再查“验签对不对”？通知根本没到服务器，改密钥、换算法全是白忙；而且通知地址配错、防火墙拦了易支付 IP 这类问题，日志里一眼就能看出来，排在签名之前最省时间。

## 坑一：密钥填错地方，或者两边密钥不一致

最常见的验签失败原因就是密钥不一致：面板后台填的易支付密钥，和易支付商户后台生成的那一份不是同一串。复制密钥时多带了一个空格、少复制了末尾一位，或者在面板里改了密钥却忘了同步改易支付后台，都会导致算出来的签名永远对不上。

还有一种隐蔽情况：有的面板把“商户 ID”和“密钥”分成两个字段，有的易支付服务商还会区分 MD5 密钥和 RSA 密钥。把 RSA 私钥填进 MD5 密钥框，或者反过来，签名算法从一开始就是错的。

```bash
# 核对密钥的操作顺序
# 1. 登录易支付商户后台，重新复制一次当前有效的密钥（不要凭记忆手打）
# 2. 粘贴到面板支付配置的对应字段，粘贴后检查首尾有没有多余空格或换行
# 3. 确认面板里选的签名方式（MD5 或 RSA）和易支付后台一致
# 4. 保存后用一笔小额真实订单测试，不要只在测试模式里自测
```

> 为什么必须重新复制而不是核对旧的？密钥这种长字符串肉眼根本看不出差一位，重新复制一次比逐字比对可靠得多；而且有的服务商在后台点过“重置密钥”后，旧密钥就失效了，面板里留的还是旧串。

## 坑二：签名算法与参数拼接方式不对

密钥对了，签名还是失败，第二要查的就是签名算法本身。易支付常见的签名方式是 MD5：把除 sign 和 sign_type 之外的所有参数按参数名升序排列，拼成 `key=value` 并用 `&` 连接，最后在末尾拼上密钥，再算 MD5。RSA 方式则是用私钥对拼接好的字符串签名、公钥验签，逻辑不同，绝不能混用。

容易踩的细节有三个：一是参与签名的参数范围，有的实现会把空值参数也拼进去，有的会跳过空值，两边规则必须一致；二是参数排序，升序排列时大小写敏感，排错一个位置签名就全变；三是字符编码，中文参数（如商品名称）如果一边是 UTF-8、一边是 GBK，算出来的签名必然不同。

```text
# MD5 签名拼接的通用思路（以你所用易支付文档为准，不要凭印象改规则）
# 1. 取出通知参数，去掉 sign 和 sign_type 两个字段
# 2. 其余参数按参数名升序排列，空值参数是否参与以文档为准
# 3. 拼成 key1=value1&key2=value2 的形式，末尾追加密钥
# 4. 对整串做 MD5，与通知里的 sign 比对
# 注意：拼接时不要对参数值再做一次 URL 编码，除非文档明确要求
```

> 为什么拼接规则必须照文档来、不能“差不多就行”？签名就是把一串字符算成摘要，改一个字符、换一个顺序、多个空格，摘要就完全不同。验签没有“接近通过”这回事，规则差一点就是 100% 失败。

## 坑三：通知地址配错，或者被挡在门外

如果日志里根本收不到通知，先查三个地方。第一是 notify_url 本身：是不是填了面板能从公网访问的完整地址，域名有没有解析到面板服务器，路径是不是面板实际的回调接口。把内网地址、带端口的测试地址填上去，易支付服务器在公网根本连不上。

第二是 HTTPS 与证书：通知地址如果是 HTTPS，证书过期、域名与证书不匹配，都会让易支付的回调请求在握手阶段就失败。第三是防火墙与安全组：服务器只放行了 80、443 给浏览器访问，却没意识到易支付回调也是从公网来的请求，或者面板机前面还有一层只放行面板 IP 的规则，把易支付服务器 IP 也拦了。

```bash
# 通知地址自查清单
# 1. notify_url 示例：https://panel.example.com/api/payment/notify
#    （域名、路径换成你自己的；不要填 127.0.0.1、内网 IP 或测试端口）
# 2. 在服务器上 curl 一下这个地址，看是否能正常响应（返回验签失败也算“通了”）
# 3. 检查证书是否过期：证书过期会让 HTTPS 回调在握手阶段失败
# 4. 检查防火墙：确认没有把易支付回调服务器的 IP 挡在外面
```

> 为什么 curl 返回“验签失败”也算通了？那说明请求已经到达你的回调接口、程序也跑起来了，剩下只是签名环节的问题；如果 curl 根本连不上，问题还在网络和地址层面，两类问题修法完全不同。

## 坑四：重复通知与并发，导致订单状态错乱

验签通过了，还有一类坑在后面：易支付在没收到“成功”响应时会按间隔重发通知，同一笔支付可能推好几次。如果面板的处理逻辑是“收到通知就加一次开通时长”，重复通知就会给用户多开通几次；如果处理时没加锁，几条通知同时到达还可能把订单状态写乱。

正确的做法是两条：第一，验签通过且订单处理成功后，立即按易支付要求的格式返回成功标识，让对方停止重发；第二，处理前先判断订单状态——已经是“已支付”的订单，再收到通知直接返回成功，不再重复开通。处理之前改一次数据库、备份一次，万一写乱了还能回滚，具体步骤可以对照本仓库的 [Xboard 数据库备份：MySQL 导出导入实操](xboard-mysql-backup.md) 先走一遍。

```text
# 异步通知处理的正确顺序
# 1. 验签：签名不一致 -> 直接返回失败，不动订单
# 2. 查单：订单号不存在，或金额与数据库不一致 -> 返回失败并记日志报警
# 3. 幂等判断：订单已是已支付状态 -> 直接返回成功，不重复开通
# 4. 开通：把订单置为已支付、开通套餐，整个过程用数据库事务包起来
# 5. 回执：处理成功后按文档要求返回成功标识，让易支付停止重发
```

> 为什么幂等判断必须放在开通之前？重发通知是易支付的正常机制，不是 bug；没有幂等判断，等于把“对方多推几次”这个正常行为，变成了“给用户多送时长”的 bug，而且事后对账很难追回。

## 验证：拿一笔真实小额订单走完全流程

改完配置不要直接放给全站用户，先做一轮真实测试。测试模式只能验证参数格式，很多服务商的测试通知和真实通知走的签名规则并不完全相同，真正能证明对接通了的，永远是一笔真实付款。

```bash
# 上线前验证清单
# 1. 用一个测试账号下一笔最小金额的真实订单，完成付款
# 2. 确认面板订单在几十秒内自动变成已支付，套餐自动开通，不用手动补单
# 3. 在易支付后台确认这笔通知显示为成功，没有重发记录
# 4. 故意用错误签名向回调地址发一次测试请求，确认面板拒绝且订单状态不动
# 5. 检查日志：这笔订单从收到通知、验签、查单到开通，每一步都有记录
```

> 为什么第 4 步要故意发一次错误签名？验签逻辑如果写反了——比如验签失败也照样开通——平时测试全是正常付款，根本发现不了；只有错误签名也被挡下，才能证明验签这道门真的在起作用。

## 常见坑汇总

- **密钥两边不一致**：复制时多空格、少一位，或者重置密钥后只改了一边，签名永远对不上，重新复制一次比肉眼比对可靠。
- **签名算法混用**：MD5 密钥填进 RSA 框、或反过来，算法从一开始就是错的，先确认两边选的是同一种。
- **参数拼接规则不对**：排序、空值处理、编码方式差一点，签名就全变，一切以易支付文档为准。
- **notify_url 填错**：内网地址、测试端口、域名未解析，通知根本到不了服务器，先查日志有没有收到请求。
- **证书过期**：HTTPS 回调在握手阶段失败，日志里连请求都没有，容易误当成验签问题。
- **防火墙拦了回调 IP**：只放行浏览器访问、没放行易支付服务器，通知会被挡在门外。
- **同步跳转当开通依据**：用户付款后关页面就不走跳转，开通必须以异步通知为准，跳转页只做展示。
- **没有幂等处理**：重发通知导致重复开通，处理前先判断订单是否已是已支付状态。
- **验签失败也照样开通**：等于把支付回调的大门敞开，错误签名必须拒绝且不动订单。
- **只在测试模式自测**：测试通知和真实通知的签名规则可能不同，上线前必须走一笔真实小额订单。
- **日志记不全**：收到通知、验签结果、查单结果、开通结果缺了任何一步，出问题后只能靠猜，每一步都要落日志。

异步通知验签看着是支付细节，其实是整个收款链路的生死线：验签太松，伪造通知就能白嫖开通；验签配错，真实付款又开不了通。按“先确认收到、再核对密钥和算法、最后处理重复通知”的顺序查一遍，再用一笔真实小额订单验证通过，这条链路才算真正接通。

# V2bX 在 Debian 12 上报 too many open files：句柄数与连接数调优

节点跑了一段时间后突然开始掉连接，面板偶尔显示节点离线又自己恢复，节点端日志里反复出现 `too many open files`。这句话的意思不是磁盘满了，也不是内存不够，而是进程打开的文件描述符（句柄）达到了上限。Linux 里每一条网络连接、每一个打开的文件、每一条管道都会占一个句柄，节点端本来就是高并发进程：用户一多、连接一多，句柄消耗就上去了。Debian 12 下这个问题尤其容易踩坑，因为限制分了好几层——系统级、用户级、systemd 服务级各管各的，只改其中一层，另一层还是会把你拦下来。本篇按“先确认、再定位、后调优、最后验证”的顺序走，不建议一上来就把所有限制都改成最大值，那样掩盖了真正的泄漏或异常连接问题。

## 先定性：确认报错确实是句柄耗尽，而不是端口或网络问题

`too many open files` 有几个典型表现：新连接建不起来、已有连接陆续断开、面板上报时断时续、重启节点端后立刻恢复、过一段时间又复发。重启能暂时恢复，是因为重启清空了已打开的句柄；过一段时间复发，说明句柄是在运行中不断累积的，或者并发一上来就撞上限。

```bash
# 先看报错是不是集中在 open files / file descriptor 上
journalctl -u v2bx -n 300 --no-pager | grep -iE 'too many open files|file descriptor|EMFILE|accept.*error'

# 确认服务在跑，排除服务本身挂掉导致的连锁现象
systemctl status v2bx --no-pager
```

如果日志里同时有大量连接超时、连接被拒绝、TLS 握手失败，那要先排除端口没放行、证书问题、IP 被封这类原因，可以先按离线排查的思路走一遍：[V2bX 对接失败：面板显示节点离线怎么办](guides/v2bx-offline-troubleshoot.md)。如果服务在跑、端口能通、报错清一色是句柄相关，而且表现是“人多时出问题、人少时没事”，那就可以锁定在句柄上限上，按本篇往下查。

还有一点要先区分：句柄耗尽分两种。一种是并发真的很高，正常连接就把上限吃满了，这是容量问题，调大上限就能解决。另一种是连接没有正常释放——比如客户端异常断开后连接挂在半关闭状态、某个上游反复重连、节点端版本有句柄泄漏——句柄数会一直往上涨，调大上限只是把复发时间往后推。调优之前先看一眼句柄数的变化趋势，再决定是单纯调大，还是要先处理异常连接。

## 第一步：看清现在到底用了多少、还剩多少

调优之前先拿到三个数字：当前进程实际打开了多少句柄、该进程的软限制是多少、硬限制是多少。软限制是实际生效的上限，硬限制是软限制最多能调到的天花板，两个都要看，只看一个容易误判。

```bash
# 找出 V2bX 主进程的 PID
pgrep -a -f v2bx | head -5

# 看该进程当前打开的句柄数（把 PID 换成你自己的）
ls /proc/<PID>/fd | wc -l
cat /proc/<PID>/limits | grep -i 'open files'

# 看系统级总量限制和当前全系统已用句柄数
cat /proc/sys/fs/file-max
cat /proc/sys/fs/file-nr
```

这几个数字的读法是：`ls /proc/<PID>/fd | wc -l` 接近 `limits` 里软限制的数字，就说明确实撞上限了；全系统 `file-nr` 的第一个数字接近 `file-max`，说明是系统总量先耗尽，这种情况要先调系统级参数，而不是只调单个服务。Debian 12 默认的系统总量通常够用，单个服务先撞上限才是更常见的情况，但跳过这一步直接调服务级限制，系统总量不足时照样会复发。

再看一眼句柄数随时间的变化，判断是容量问题还是泄漏问题：

```bash
# 每 10 秒采一次，连续看几分钟，观察句柄数是平稳还是单调上涨
for i in 1 2 3 4 5 6; do
  echo -n "$(date '+%H:%M:%S') "
  ls /proc/<PID>/fd | wc -l
  sleep 10
done
```

人少时平稳、人多时随并发上涨，涨到上限附近就报错，这是容量问题；即使没什么人用，句柄数也在缓慢单调上涨、重启后又从低位重新涨，这是泄漏或连接不释放的问题。后一种情况调大上限只能缓解，要同时去查异常连接来源，比如某个客户端或某条中转链路在反复建连，处理掉源头再调上限。

## 第二步：找出是哪一层限制在拦你

Debian 12 上 V2bX 的句柄限制至少有三层，改错层等于白改。排查顺序是从服务本身往外：先看 systemd 服务的限制，再看用户级限制，最后看系统级参数。

```bash
# 1. systemd 服务级：看 v2bx 服务实际生效的限制
systemctl show v2bx -p LimitNOFILE

# 2. 用户级：看 limits 配置里有没有针对该用户的限制
grep -R 'nofile' /etc/security/limits.conf /etc/security/limits.d/ 2>/dev/null

# 3. 系统级：看内核总量与单个进程能打开的最大值
cat /proc/sys/fs/file-max
cat /proc/sys/fs/nr_open
```

为什么分层这么重要：systemd 启动的服务不走登录会话的 PAM limits，`/etc/security/limits.conf` 里写得再大，systemd 服务也读不到；反过来，只改 systemd 的 `LimitNOFILE`，系统总量 `file-max` 不够时还是会报错。很多教程只给其中一层，照抄后发现“改了没生效”，往往就是层没对上。先用 `systemctl show` 确认服务实际生效的数字，再决定改哪一层，不要凭感觉改。

如果 `systemctl show` 输出的 `LimitNOFILE` 只有 1024 或 4096，而进程实际句柄数已经顶到这个数附近，问题就很明确了：Debian 12 下 systemd 服务的默认句柄限制偏低，高并发节点端很容易撞线。这是最常见的根因，优先处理这一层。

## 第三步：调优——按层改，改完重载服务

调优的原则是分层改、改够用就好，不要一步拉到几百万。节点端的合理起点是 65535 或 131072，具体看你的并发规模：几百人同时在线，65535 通常够用；上千并发、且每用户多连接时，再往 131072 或 262144 考虑。改完要重载 systemd 配置并重启服务，只改文件不重启，旧进程还是跑在旧限制下。

先改 systemd 服务级，这是最关键的一层。用 `systemctl edit` 生成覆盖配置，不要直接改动原始服务文件，这样以后更新服务文件时你的改动不会被覆盖：

```bash
systemctl edit v2bx
```

在打开的编辑器里写入：

```ini
[Service]
LimitNOFILE=131072
```

`LimitNOFILE` 就是 systemd 里控制单个服务最大打开文件数的参数，写在这里只影响 v2bx 这一个服务，不会放宽系统上其他服务的限制，这是它比全局改 limits 更安全的原因。保存后重载并重启：

```bash
systemctl daemon-reload
systemctl restart v2bx
systemctl show v2bx -p LimitNOFILE
cat /proc/$(pgrep -f v2bx | head -1)/limits | grep -i 'open files'
```

最后两条命令是硬验证：`systemctl show` 看配置生效了没有，`/proc/<PID>/limits` 看新进程实际跑在什么限制下。两个数字都对上，才算这一层真正改好了；只看配置文件写进去了，不等于生效。

如果全系统总量也不够，再调系统级参数。把配置写进 `/etc/sysctl.d/` 下的独立文件，不要直接改 `/etc/sysctl.conf`，独立文件更容易回滚：

```bash
cat > /etc/sysctl.d/99-file-max.conf <<'EOF'
fs.file-max = 1000000
EOF
sysctl -p /etc/sysctl.d/99-file-max.conf
cat /proc/sys/fs/file-max
```

`fs.file-max` 是全系统所有进程能打开的句柄总量上限，调大它只是抬高天花板，不会让单个进程自动获得更多额度，单个进程的额度还是由它自己的软限制决定。所以系统级和服务级要配合着看：系统总量要大于所有服务需求之和，服务级要大于单个节点的实际并发需求。

用户级 limits 只在一种情况下需要动：你不是用 systemd 跑 V2bX，而是手动在 shell 里启动，或者用其他 supervisor 启动且它走 PAM limits。如果是 systemd 方式，改完服务级就够了，不用再去动 `/etc/security/limits.conf`。非 systemd 方式启动时，才需要确认：

```bash
# 手动启动的进程，看当前 shell 的限制
ulimit -n
ulimit -Hn
```

`ulimit -n` 是当前 shell 的软限制，手动启动的进程会继承它；软限制低于需求时，可以在启动脚本里先执行 `ulimit -n 131072` 再启动进程。注意软限制不能超过硬限制，硬限制要 root 才能抬高，普通用户改不动，这是很多人“ulimit 改了又变回去”的原因——改的是当前 shell，换个会话就失效了，要写进启动脚本才持久。

## 第四步：别只调上限——顺带收紧异常连接

如果第二步观察到句柄数单调上涨、或者并发并不高却频繁撞上限，调大上限的同时要收紧异常连接，否则上限迟早还会再撞一次。先看句柄都耗在什么类型的连接上：

```bash
# 看该进程的 TCP 连接状态分布，TIME_WAIT 或 CLOSE_WAIT 异常多就是线索
ss -tanp | grep v2bx | awk '{print $1}' | sort | uniq -c | sort -rn

# 看哪些远端地址建了最多的连接，判断是不是个别源在反复建连
ss -tanp | grep v2bx | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn | head -20
```

`TIME_WAIT` 堆积多，通常是短连接频繁建连、端口复用没开；`CLOSE_WAIT` 堆积多，通常是对端已经关闭、本地应用没有及时关闭连接，这类问题要结合节点端与上游的配置看，不能只靠调内核参数。`ss` 结果里某一个 IP 占了几百上千条连接，先确认它是正常的中转机还是异常建连：中转机本身就会聚合很多用户连接，单 IP 连接数高不一定是攻击，不要一上来就封 IP，先对照面板里的节点与中转关系确认。

内核层可以顺带开 TCP 复用与回收，减少 `TIME_WAIT` 堆积，但要写进 sysctl 持久化文件，不要只用命令行临时改：

```bash
cat > /etc/sysctl.d/99-tcp-tuning.conf <<'EOF'
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_fin_timeout = 30
EOF
sysctl -p /etc/sysctl.d/99-tcp-tuning.conf
```

`tcp_tw_reuse` 允许复用处于 `TIME_WAIT` 状态的连接，缓解短连接频繁建连时的端口与句柄压力；`tcp_fin_timeout` 把 FIN 等待超时从默认的 60 秒缩短到 30 秒，让半关闭连接更快释放。这两个参数是缓解，不是根治——连接泄漏的源头还是要找到，否则只是把复发周期拉长。

## 第五步：验证——压到上限附近也不报错才算过关

调完不要只看限制数字变大了就收工，要验证三件事：新限制确实生效、正常并发下句柄数离上限有余量、日志里不再刷句柄报错。

```bash
# 1. 新进程的实际限制已经是新值
cat /proc/$(pgrep -f v2bx | head -1)/limits | grep -i 'open files'

# 2. 跑一段时间后再看句柄占用，确认离上限有余量
ls /proc/$(pgrep -f v2bx | head -1)/fd | wc -l

# 3. 日志里不再出现句柄报错
journalctl -u v2bx -n 200 --no-pager | grep -iE 'too many open files|EMFILE' || echo "no open-files errors"

# 4. 等一个上报周期，确认面板里节点在线、流量正常上报
```

第 2 项的判断标准是：高峰期句柄占用最好不超过上限的 70%。长期贴着上限跑，突发并发一来还是会撞线，那时再临时调就来不及了，宁可一开始就留出余量。第 3 项要至少观察一个完整的高峰时段再下结论，刚重启时没报错很正常，因为句柄数还没涨起来；高峰过去、日志干净，才算真正过关。验证时顺带确认订阅能正常拉取、已有用户没有大面积掉线，调优本身不应该影响正常连接。

## 常见坑

- **只改 limits.conf，systemd 服务不认**：systemd 启动的服务不走 PAM limits，改 limits.conf 对 v2bx 服务无效，必须改 `LimitNOFILE`。
- **只改配置文件不重启**：旧进程还跑在旧限制下，改完必须 `daemon-reload` 加重启服务，新进程才生效。
- **直接改原始服务文件**：更新时会把改动覆盖掉，用 `systemctl edit` 生成覆盖配置才是持久的做法。
- **软限制与硬限制混淆**：实际生效的是软限制，`ulimit` 改软限制改不过硬限制，硬限制要 root 抬。
- **系统总量不够只调服务级**：全系统 `file-max` 先耗尽时，单个服务调再大也没用，两层要一起看。
- **一味拉到最大值**：把上限拉到几百万，掩盖了连接泄漏，复发时更难定位，先看趋势再定数值。
- **把中转机当攻击封掉**：单 IP 连接数高可能是正常的中转聚合，先对照面板里的节点关系再处理。
- **临时 sysctl 不持久**：命令行 `sysctl -w` 重启就失效，写进 `/etc/sysctl.d/` 的文件才会在重启后还在。
- **只看配置不看实际进程限制**：配置文件写对了不等于生效，一定要用 `/proc/<PID>/limits` 核对新进程。

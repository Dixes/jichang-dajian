# Xboard 订阅链接返回 404：路由、缓存与反代排查

面板后台能正常打开、用户能登录，偏偏订阅链接一拉就返回 404：客户端显示订阅获取失败，节点列表空空如也。这种情况最折磨人，因为面板本身没挂，问题藏在订阅链接从“发出请求”到“生成内容”的链路上：链接本身写错了、面板路由缓存还是旧的、反代把订阅路径截断了，三种原因表现出来都是同一个 404。直接重启面板、重装节点端，大概率白折腾一圈，404 还在原地。

排查要按请求走过的顺序分层：先确认订阅链接本身对不对，再看面板这一层能不能生成订阅，最后看反代有没有把请求正确送到面板。每一层单独验证，定位到哪一层再修哪一层，不要三层一起改——一起改完 404 没了，你也不知道是哪一处修好的，下次再出同样问题还是从头猜。

## 先分清：404 来自哪一层

同样是 404，不同层的表现其实不一样，动手之前先用 `curl` 看一眼，省掉很多弯路：

```bash
# 直接请求订阅链接，只看响应头，确认状态码和 Server 信息
curl -I "https://panel.example.com/api/v1/client/subscribe?token=TEST_TOKEN"
```

如果响应头里 Server 是 nginx，并且返回体是 Nginx 默认的 404 页面，说明请求根本没到面板，是反代这一层就把它拦下来了，或者反代把路径转错了地方。如果响应头里有面板的特征、返回体是面板返回的 JSON 错误（比如提示订阅不存在），说明请求已经到了面板，是面板这一层找不到对应的订阅。分不清这一层就动手，很容易在面板这边改半天，问题其实在反代配置里。

还有一种情况要先排除：订阅链接本身就是旧的、错的。比如用户手里保存的是换域名之前的旧订阅地址，旧域名已经停了反代，或者 token 已经被重置过——这种 404 跟面板、反代都没关系，修配置永远修不好。先拿面板后台新生成的订阅链接实测一遍，确认新链接也 404，再往下排查；如果只有老链接 404、新链接正常，问题就是链接过期或域名已换，走订阅迁移的路子，而不是修面板。

## 第一步：确认订阅链接本身对不对

订阅链接由三部分组成：面板域名、订阅路径、token 参数，任何一部分错了都会 404。逐项核对，不要只看链接“大概像”：

```bash
# 1. 域名解析对不对，返回的 IP 应该是面板机的 IP
dig +short panel.example.com

# 2. 域名 HTTPS 通不通，证书是不是面板域名的
curl -I https://panel.example.com

# 3. 拿面板后台刚生成的订阅链接实测（把 token 换成真实的测试 token）
curl -s "https://panel.example.com/api/v1/client/subscribe?token=TEST_TOKEN" | head -c 500
```

`dig +short` 返回面板机 IP，说明解析没问题；如果返回的是别的 IP，订阅请求根本没发到面板机，查解析记录，而不是查面板。`curl -I https://panel.example.com` 能返回 200，说明域名和证书这一层是通的；如果这里就报证书域名不匹配，先修证书，不要急着查订阅路由。第三条命令输出订阅内容，说明链接本身没问题；输出 404，才进入下一层排查。

token 也要单独验证：token 拼错一个字符、多了空格、复制时把链接截断了，面板都认不出来，返回的也是 404。验证时不要用用户发来的、可能被聊天工具截断的链接，直接从面板后台复制一条新链接测试。用户账号状态也要看一眼：账号过期、被禁用、套餐流量用完的账号，订阅接口可能直接拒绝生成，表现也可能是 404 或者空订阅——先确认测试账号是正常有效的，再断定是路由或反代的问题。

## 第二步：查面板路由与缓存

链接没问题、请求也到了面板，但面板还是返回 404，接下来查面板的路由和缓存。Xboard 这类 Laravel 面板，路由和配置都有缓存：刚升级面板、刚改过路由、刚迁移过数据之后，缓存还是旧的，新路由没生效，订阅路径在旧路由表里根本不存在，就会 404。重启面板服务并不能清掉文件缓存，必须手动清：

```bash
# 进面板目录，清掉路由缓存和配置缓存，再重新生成
cd /opt/xboard
php artisan route:clear
php artisan config:clear
php artisan cache:clear
php artisan route:cache
php artisan config:cache
```

`route:clear` 和 `config:clear` 是把旧缓存文件删掉，让面板下次按当前代码和配置重新加载；`route:cache` 和 `config:cache` 是重新生成缓存，让正式运行更快。只清不重建也可以跑，但正式环境建议重建，否则每次请求都重新解析路由，面板会变慢。清缓存之后要重启队列和面板服务，只清文件不重启，跑着的旧进程可能还拿着旧缓存：

```bash
# 重启面板服务和队列（按你自己的部署方式，supervisor 或 systemd 二选一）
supervisorctl restart all
# 或者
systemctl restart xboard
```

清完缓存再用测试订阅链接请求一次。如果 404 变成了正常订阅内容，问题就是路由或配置缓存陈旧，以后每次升级面板、改配置之后，都把清缓存列为固定步骤。如果清完缓存还是 404，再看面板日志——日志会告诉你是路由没匹配上，还是订阅生成时在数据库那一步卡住了：

```bash
# 看面板最近的错误日志，找 subscribe、404、路由相关的记录
tail -n 200 /opt/xboard/storage/logs/laravel.log | grep -i "subscribe\|404\|not found"
```

日志里如果出现路由未匹配、控制器不存在，说明面板代码或升级过程有问题，可能是升级没完成、文件没覆盖全；如果出现数据库连接失败、订阅表查询报错，说明问题在数据库那一层，要按数据库方向排查，而不是继续折腾路由。日志里什么都没有、请求也没落到面板日志里，那请求根本没到面板，回到反代那一层查。

## 第三步：查反代有没有把订阅路径送对

请求没到面板，或者到了面板但路径变了，问题多半在反代。最常见的反代坑有三个：location 只配了 `/` 却没正确透传、反代配置里写了 `try_files` 把 API 请求当成静态文件处理、反代后面挂了多个 server 块，订阅请求被别的 server 块抢走了。

```nginx
# 面板反代的正确写法示例：订阅路径和普通页面走同一条代理
server {
    listen 443 ssl;
    server_name panel.example.com;

    ssl_certificate /etc/letsencrypt/live/panel.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/panel.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

`proxy_pass http://127.0.0.1:8080` 后面不带路径，意思是把请求原路径原样送给面板，`/api/v1/client/subscribe` 到面板还是这条路径。如果写成了 `proxy_pass http://127.0.0.1:8080/;`（末尾多了斜杠）或者 `proxy_pass http://127.0.0.1:8080/panel;`，反代会把路径改写，面板收到的路径就不是订阅路径，自然 404。`proxy_set_header Host $host` 也要保留，面板靠 Host 判断站点和生成订阅链接，Host 写死或者没传，订阅生成也可能出错。

检查时先确认反代配置里有没有给 `/api/` 单独写 location：如果有单独的 `/api/` location，它可能指向了别的后端、或者加了 `try_files $uri =404;`，API 请求还没到面板就被当成静态文件 404 了。单独的 API location 要么删掉、让它走统一的 `/` 代理，要么确认它的 proxy_pass 也指向面板。改完反代配置要检查语法再重载，只改文件不重载，跑的还是旧配置：

```bash
# 检查配置语法，通过后再重载
nginx -t && systemctl reload nginx
```

反代排查还有一个容易漏的点：面板前面如果挂了 Cloudflare，橙云模式下 Cloudflare 的缓存规则、页面规则可能把订阅接口缓存成 404，或者把订阅请求拦掉。排查时可以临时切到灰云、绕过 Cloudflare 直接请求源站 IP 对比一次，如果直连源站正常、走 Cloudflare 就 404，问题就在 Cloudflare 那一层。反代报 502 和订阅 404 的排查思路有相通之处，502 的上游端口与超时排查可以对照这篇：[Nginx 反代面板出现 502 Bad Gateway：上游端口与超时排查](guides/nginx-panel-502-troubleshoot.md)。

## 验证：按真实链路走一遍

三层都查完、改完之后，不要只在服务器上 `curl` 一下就收工，要按用户真实使用的链路验证：

```bash
# 1. 面板后台新生成的订阅链接，curl 能拉到订阅内容
# 2. 老用户手里已有的订阅链接（未过期、未换域名）也能正常拉取
# 3. 客户端刷新订阅后，节点列表数量和面板后台一致
# 4. 新注册测试账号的订阅链接同样能拉取，不只是管理员账号能用
```

只验证管理员账号是不够的：管理员账号、测试账号、普通用户账号走的权限和套餐状态不一样，管理员能拉、普通用户拉不到的情况并不少见。验证时分账号、分新旧链接各走一遍，全部通过才算修好。验证通过之后，把这次的定位记下来：是哪一层的问题、改了哪处配置、清缓存有没有生效——下次再出 404，先看这份记录，能省掉一半排查时间。

## 常见坑

- **只重启面板，不清路由缓存**：升级后面板路由缓存还是旧的，订阅路径在旧路由表里不存在，重启多少次都是 404。
- **拿用户发来的旧链接测试**：旧链接可能 token 已重置、域名已换，测它永远是 404，要用面板后台新生成的链接测试。
- **反代 proxy_pass 末尾多了斜杠或路径**：路径被改写，面板收到的不是订阅路径，删掉多余的路径部分，让请求原样透传。
- **反代给 /api/ 单独配了 location**：单独的 API location 可能指向别的后端或加了 try_files，要么删掉、要么确认它也指向面板。
- **改了反代配置没重载**：文件改了、服务没 reload，跑的还是旧配置，验证时看到的还是旧行为。
- **面板日志没看就动手改**：日志能直接告诉你是路由没匹配、还是数据库报错，不看日志就改配置，等于闭眼修。
- **账号过期、被禁用也当成路由问题**：先确认测试账号正常有效，再断定是路由或反代的问题。
- **只验证管理员账号**：普通用户账号的权限和套餐状态不一样，管理员能拉不代表所有用户都能拉。
- **域名证书问题和订阅 404 混在一起**：证书域名不匹配时先修证书，分开验证、分开修，不要混成一个问题。
- **Cloudflare 缓存了 404**：走 Cloudflare 404、直连源站正常时，问题在 Cloudflare 缓存或规则层，先绕过 Cloudflare 对比一次。
- **清缓存只清一半**：路由、配置、应用缓存要一起清，只清其中一项，旧缓存可能还在另一处生效。

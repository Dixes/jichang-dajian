# V2bX 报 API 密钥无效：面板与节点端密钥同步排查

节点明明在线过，换了一次面板配置、改了一次节点信息，或者重装了一次节点端，V2bX 日志里突然开始刷 `invalid API key`、`unauthorized` 一类的报错，面板上这个节点也跟着离线。很多人第一反应是面板挂了，其实更常见的原因简单得多：面板和节点端手里的密钥对不上了。下面按「先核对、再同步、最后清缓存」的顺序排查，不用重装面板，也不用重建节点。

## 先分清：密钥无效和节点离线不是一回事

面板显示节点离线只是一个结果，背后的原因有很多，防火墙、端口、协议配置都可能导致离线。先看 V2bX 的日志，确认报错里确实提到了密钥、认证、授权这类字眼，再按本篇往下走：

```bash
# 看 V2bX 最近的日志，找 invalid、unauthorized、auth 这类关键字
journalctl -u v2bx -n 200 --no-pager | grep -iE 'invalid|unauthorized|auth|api'
```

如果日志里根本没有密钥相关的报错，只是连不上、超时，那问题不在密钥上，可以先对照本仓库的另一篇教程按离线排查：[V2bX 对接失败：面板显示节点离线怎么办](guides/v2bx-offline-troubleshoot.md)。只有确认报错指向密钥，才继续下面的步骤，否则容易修错方向。

## 第一步：核对面板里的密钥到底是哪一个

密钥无效最常见的根因，是两边拿的根本不是同一把密钥：面板里改过一次，节点端还留着旧的；或者节点端复制时多了一个空格、少了一段字符。先到面板里找到这个节点的配置，把密钥的来源定下来：

1. 登录面板后台，打开这个节点的编辑页，找到 API 地址、节点 ID 和通信密钥（不同面板叫法略有差异，有的叫 API Key，有的叫节点密钥，认准「节点端向面板上报用的那一把」）。
2. 注意区分两把容易混淆的密钥：一把是面板给节点端用的通信密钥，另一把可能是面板管理员登录、支付回调或者其他接口用的密钥。节点端配置里要填的只能是前者，填错一把就会一直报无效。
3. 如果面板支持重新生成密钥，先不要急着点「重新生成」——点下去旧密钥立刻失效，所有用旧密钥的节点都会同时掉线。先把现有密钥原样抄出来，确认节点端是不是用的它。

核对时还有一个细节：密钥前后不要带空格、换行和引号。很多人从网页上复制密钥时，末尾会多带一个看不见的空格，粘贴进配置文件后就怎么都对不上。用下面的办法直接比对两边的密钥长度，长度不一致基本就是复制出了问题：

```bash
# 把面板里抄出来的密钥和节点端配置文件里的密钥分别数一下长度
# 两边长度不一样，先解决复制问题，不要急着改配置
echo -n '面板里的密钥' | wc -c
echo -n '节点端配置文件里的密钥' | wc -c
```

## 第二步：到节点端核对配置并正确重启

确认面板里的密钥无误后，到节点端打开 V2bX 的配置文件，找到对应面板的节点配置段，核对三项：面板地址、节点 ID、通信密钥。

```bash
# 找到 V2bX 的配置文件，路径以你安装时的实际路径为准
ls /etc/V2bX/
cat /etc/V2bX/config.json
```

核对时按这个顺序看：

- **面板地址**：必须是面板的完整 API 地址，域名和端口都要对。面板换过域名、加过反代路径前缀之后，旧地址即使能通，也可能走到错误的接口上，表现同样是认证失败。
- **节点 ID**：必须是面板里这个节点的 ID，不是节点名字，也不是服务器编号。面板里删掉旧节点重建一个同名节点后，ID 会变，节点端还用旧 ID 就会对不上。
- **通信密钥**：和第一步抄出来的面板密钥逐字比对，重点看首尾有没有多余空格、中间有没有被编辑器自动换行截断。

改完配置不要只保存就完事，必须重启 V2bX 让新配置生效，而且要确认重启真的成功了：

```bash
# 修改配置后重启 V2bX
systemctl restart v2bx

# 确认服务状态是 active，没有报错
systemctl status v2bx --no-pager

# 再看一次日志，确认 invalid API key 的报错不再出现
journalctl -u v2bx -n 100 --no-pager | grep -iE 'invalid|unauthorized'
```

这里有个容易踩的坑：有人改完配置用的是 `reload` 而不是 `restart`，或者改的是备份文件而不是正在运行的那份配置。重启后如果报错原样不动，先确认改的文件路径是不是服务实际加载的那一份，再往下查。

## 第三步：多节点与缓存场景的同步问题

单节点场景按前两步基本能解决，但如果你一台面板带多个节点，或者节点端前面有缓存、反代，就要多查两个地方：

**多节点不要共用一份密钥。** 面板里每个节点通常有独立的密钥或独立的节点 ID，图省事把 A 节点的密钥抄到 B 节点上，B 节点上报时面板一查 ID 和密钥对不上，就会报无效。每个节点单独建配置、单独填自己的密钥和 ID，不要跨节点复制。

**反代缓存可能让你看到旧的报错。** 面板前面如果套了反代或 CDN，节点上报走的 API 路径被缓存住时，面板改了密钥，节点端拿到的还是旧的校验结果。排查期间可以先绕过反代，让节点端直连面板源站地址验证一次：

```bash
# 在节点端本机直接请求面板 API 地址，确认源站本身能响应
# 地址和端口换成你自己的面板 API 地址
curl -I https://panel.example.com/api/v1/server
```

直连通过、走反代失败，说明问题在反代层，要去查反代有没有缓存 API 路径、有没有改写请求头；直连也失败，再回到第一步重新核对密钥和节点 ID。

还有一个少见但真实存在的原因：面板机和节点端的系统时间差得太多。有些面板的接口校验会受时间影响，时间差过大时请求会被判定无效。如果密钥、ID、地址都核对无误，可以顺手看一眼两边的时间：

```bash
# 面板机和节点端分别执行，看时间是否在同一分钟内
date
```

时间差超过几分钟就先校时，校时之后再重启一次 V2bX 验证，不要同时改密钥和改时间，否则分不清到底是哪一步修好的。

## 验证：确认节点真的重新上线

不要只看日志里报错消失就收工，按下面三步验证：

```bash
# 1. 节点端日志不再刷密钥报错，且出现上报成功的记录
journalctl -u v2bx -n 100 --no-pager | tail -50

# 2. 面板后台刷新节点列表，这个节点状态变回在线
# 3. 用一个测试订阅链接拉取一次，确认该节点的流量和在线状态正常更新
curl -s https://panel.example.com/api/v1/client/subscribe?token=YOUR_TOKEN | head -c 500
```

上面订阅地址里的域名和 token 都是占位符，换成你自己的面板域名和测试 token。节点在线、订阅能拉取、日志不再报错，三项都满足才算真正修好。只满足其中一项时，往往是另一个问题被掩盖了，比如日志安静了但面板还是离线，那就要回头查节点 ID 和面板地址。

## 常见坑

- **改了面板密钥却忘了同步节点端**：重新生成密钥后，所有用旧密钥的节点会同时掉线，改密钥之前先列出受影响的节点，逐个同步。
- **把节点 ID 当成密钥填**：面板里的节点 ID 和通信密钥是两个字段，填反了必然报无效，核对时按字段名逐项认。
- **复制密钥带了首尾空格**：网页复制最容易多带空格，粘贴后先检查首尾，长度对不上先解决复制问题。
- **改完配置没有真正重启**：只保存不重启，或者重启了错误服务，都会让旧配置继续跑，报错原样不动。
- **多节点共用同一份密钥**：每个节点用自己的密钥和 ID，跨节点复制配置是密钥报错的高发来源。
- **把密钥问题当成网络问题修**：日志没确认就去改防火墙、换端口、重装节点端，方向错了会越修越乱，先看日志定性再动手。
